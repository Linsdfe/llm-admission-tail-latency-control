# 本项目论文工作流

以下路径从项目根目录解析。按当前章节读取相关材料，不默认加载全部原始日志。

## 材料分工

| 材料 | 写作时的用途 |
|---|---|
| 根目录开题报告 Markdown | 研究问题、拟采用方法、目标与计划；不是实验结果来源 |
| 根目录开发流程计划 Markdown | 任务、预算、退出条件；实际进展注明日期 |
| docs/environment.md、docs/source-map.md | 特定日期和版本的环境、源码定位 |
| docs/prestudy*-protocol*.md、configs/ | 核对实验方案；历史运行以该批次保存的协议、配置、源码快照和偏离记录为准 |
| docs/experiments/<run_id>/ | 批次报告与结果来源索引 |
| results/raw/、results/archives/ | 本机原始证据和归档；默认不入 Git，不宣称克隆仓库即可获得完整原始数据 |
| daily/、results/README.md、README.md | 按实际日期记录进展与运行状态，不代表开题时已有成果 |

## 时间与证据

初稿编制日期不等于正式开题评审日期。正式事件以学院通知、用户确认或真实记录为依据；不倒填时间，不把后验方案写成预注册。

阶段报告明确截止日。论文结果注明运行标识、协议和分析版本，必要时标明源码版本；最新文档不能替代历史批次快照。拟定参数标为计划值，实测值取自实际记录。开题中的设备条件可以陈述已有基础，但后续运行的吞吐、延迟、显存实测和完成进展不回填到纯方案正文。

## 章节组织

学校和用户指定模板优先。没有模板时，可从以下结构出发，按实际材料调整：

1. 绪论：具体服务问题、研究问题和范围，不预先宣称收益已获证实。
2. 相关研究：比较问题、状态、控制动作、约束与证据，突出最接近的工作，不只逐篇摘要。
3. 需求与建模：定义请求类别与长度、软工作量与硬容量、系统状态、指标及计时边界。
4. 方法设计：说明设计选择、预期机制、适用前提和退化路径，区分工程基础与拟研究贡献。
5. 系统实现：陈述实际实现的接口、状态、版本及验证；未实现部分保留计划语气。
6. 实验与分析：交代实际协议、完整请求总体、效应与变异、代价、消融和失败结果，再讨论替代解释与适用边界。
7. 总结：逐项回应研究问题，区分已完成、有证据支持、尚未支持和未来工作。

具体基线与协议以当前有效方案和历史批次证据为准，不在技能中固定易变的策略名称、阈值或进度。涉及实验解释时读取 scientific-critical-thinking 的项目工作流；文字修改不自动启动新实验。

## 起草与缺口处理

关键事实和数值应能定位来源，不强制为每一句建立登记表。缺少数据时可以完成背景、问题和拟定方法，不补造结果。未核实文献先检索原文；暂时无法核实的条目保留为工作缺口，不混入正式参考文献。

检查跨章节术语、单位、分母、样本量、表图和摘要的一致性。原始证据及历史协议不覆盖；需要修正时新增版本并说明变更。不因润色自动更新阶段完成状态。

## 可选工具

随附脚本使用 Python 标准库，可离线运行，入口见 cli_reference.md。临床报告和投稿检查规则只在实际适用时使用。

仅在用户需要新建写作工作区时使用 scaffold_manuscript.py，指定新目录；不覆盖现有论文。生成的占位文字必须补充和核对，不能作为完成稿提交。
