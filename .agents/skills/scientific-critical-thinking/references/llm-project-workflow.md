# 本项目的论文实验工作流

适用项目：llm-admission-tail-latency-control。解释用通俗中文，保留必要的指标原名。

## 先确定究竟要回答哪个问题

把问题写成“在什么设备、模型和负载下，改变什么，相比什么，对哪个指标产生多大影响”。明确结果属于描述、机制解释还是因果比较。不同问题可以需要不同对照，不能把“单一变量”当成适用于所有研究的唯一设计原则；多因素实验也可以有效，但必须能识别所要估计的效应。

本项目至少要区分：

| 问题 | 主要干预 | 设计重点 | 不能自动推出 |
|---|---|---|---|
| 加入指定额外任务的整体影响 | 加入预定义后台工作负载 | 固定交互轨迹、服务设置，平衡执行顺序并重复 | 后台业务标签或请求长度的独立作用 |
| 负载强度与等待的关系 | 后台计划到达率 | 固定提示词与长度生成规则，预先选负载水平 | 长短异质性的独立效应 |
| 长度分布的影响 | 预先指定的长度分配方案 | 尽量匹配请求数、到达轨迹、输入及预设输出总预算，检查实际执行 | 只要总 token 相等就等于计算量完全相等 |
| 调度策略是否有效 | 调度策略 | 相同预定工作负载、版本、容量和计时，配对与顺序平衡 | 只改善已完成请求就代表系统整体更好 |

增加后台任务会自然增加请求数、到达率和工作量。这些可能是“加入这批工作”的组成部分或作用路径，不应一概叫成外部混杂因素。时间漂移、温度、缓存及宿主竞争等则可能干扰条件间比较。先定义目标效应，再判断哪些量需要固定、哪些是干预结果。

“后台”是业务标签。基线若不读取标签，单纯改标签不会定义出长度或工作量的效果；策略若按标签区别处理，则要明确这是另一种干预。

## 本项目的现有证据边界

阅读项目根目录下的 `docs/p0-g0-review.md`、`docs/prestudy-protocol.md`、`configs/prestudy-e0e1.json` 和 `docs/experiments/20261020-234210-p0-e0e1/README.md`。数字以同目录 `summary.json` 和原始记录为准。此处路径从项目根目录解析。

目前 E0 是200条交互，E1 是相同交互加100条后台。三组共1500条测量请求，12条预热排除；E1 每轮实际总输出41848 token，E0 为3985 token。三组重复属于探索性证据，不能把1500条共享队列的请求视为1500次独立实验。G0 待复审，自研 C++ 调度尚未完成。

可以报告“两条件间交互等待的差异”，也可以讨论在明确假设下加入这批工作负载的整体影响。当前设计未分离总工作量、长度分布与过载机制，不能把全部差异归因于后台身份或长度异质性。因果解释需要说明执行顺序、重复、环境稳定性及其限制，不能仅因不是严格单一变量就断言任何因果研究都不可能。

## 开跑之前写一张简明实验卡

新增协议放到 `docs/` 合适位置，避免覆盖原协议。至少写清：

1. 研究问题、可检验假设、主指标和有实际意义的变化幅度。
2. 独立实验单位、重复方式、配对方法、执行顺序以及如何处理时间漂移。共享一次队列的请求存在依赖。
3. 自变量及水平；固定项；预计连带变化；难以控制的因素及补救措施。
4. 每个场景的请求数、到达轨迹、输入量、输出预算、缓存、slot、上下文和容量边界。
5. 预热、发送滞后门槛、总超时、统一截止、窗口、排空、六类终态和排除规则。
6. 校准、开发、最终测试如何分开；负载和参数如何确定；失败与未完成如何报告。
7. 最小有用矩阵、预计机时、磁盘及停止条件。P0 只补与可行性判断直接有关的证据，不自动扩成正式全矩阵。

控制实际长度时，`max_tokens` 只是上限；temperature=0 也不能替代实际长度与缓存核对。如果采用强制长度、忽略 EOS 或模拟负载，先确认引擎确实支持，并注明与自然生成的差别。输入位置、prefill/decode 构成、缓存和批处理会影响代价，总 token 相等不能保证实际算力占用一致。

不要看完结果后删选请求，强行凑成“相同实际输出量”。实际输出、吞吐或 GPU 使用可能受到策略影响，不能为了匹配它们而抹去策略的真实作用路径。优先固定干预前可指定的请求与预算，再报告实际量的差异和敏感性分析。

## 跑完先核对再解释

- 记录实际发送、首段非空内容、结束、输入/缓存/输出 token、全部终态及对应版本。TTFT 从实际发送至首段生成内容，不能用响应头代替。
- 全部时间使用约定边界和同一可比较时钟；客户端相对时钟不直接与 GPU/服务墙钟相减。
- 核对计划数与终态合计、逐请求文件、迟发、容量、异常和退出码。保留失败运行；重跑新增 run_id，写明原因。
- 按轮报告配对差异和波动。统计方法尊重请求时间依赖和独立运行层级；若使用置信区间或重采样，解释重采样单位，避免对共享队列请求盲目逐条 bootstrap。
- P95 的样本范围、插值算法、完成样本与失败样本的处理提前明确。超时不能静默消失，不能仅报完成者延迟。
- 吞吐量写清单位和分母。100秒窗口完成率与包含排空的全程 token/s 分开报告。单看吞吐不能代替交互等待和后台代价。

## 写入论文或总结时

方法写“比较什么、怎样控制、如何测量”；结果写实际数值、样本分母、重复和波动；讨论写可能机制与替代解释；局限写不能区分的因素和适用范围。观察、解释与未来计划分别表达。

每个结论标明 run_id、来源文件、版本和计时口径。引用真实可核验文献，不虚构引文；探索后形成的假设注明来源，不冒充事先假设。正文尽量通俗，名词第一次出现时解释。

Word 任务使用可用文档工具并逐页检查，保留同内容 Markdown。每日归档与进度更新按项目的 `skills/llm-project-daily/SKILL.md` 执行，完整原始数据和日期包不因清理删除。仅更新文档或安装技能，不自动标记 G0 通过，也不自动启动实验或推送。

## 建议的审查输出

给出：当前问题和允许的结论、变量与对照表、最大解释缺口、最小补充方案、验收和机时、论文措辞。无需为了形式把每项写成长文。无法严格控制时说明可识别到什么程度，不承诺“完全消除混杂”。
