## 1. 复审结论与来源

P0 已经提供可信的客户端测量基础，并重复观察到加入指定后台工作负载后交互 TTFT 大幅增加。最需要补充的是：**降低后台到达强度、减少持续积压后，是否仍有值得研究的交互尾延迟损失。** 暂不把任务扩大为长度机制识别或调度策略验证。

本次读取了原协议、配置、汇总、分析及回放源码，核对六轮原始逐请求文件数量为 200、300、200、300、200、300，并抽查 r1-E1 的 B000 原始记录。本轮没有重新执行原审计脚本或逐一重验全部原始文件哈希；原批次 `audit_status=passed` 是既有审计结果。

### 已验证事实

- 每轮 E0 为 200 条交互；E1 为相同交互加 100 条后台。六轮各自重新启动服务，12 条预热不计测量样本。
- E0 交互 P95 为 33.860–36.190 ms；E1 为 111054.321–123727.800 ms。配对差值为 111019.723、123691.610、111631.646 ms。
- 每轮 E0 实际输出 3985 token；E1 为 4010+37838=41848 token，约为 E0 的 10.50 倍。E1 排空为 117.568–130.675 s。
- 全部 1500 条测量请求最终完成、没有其他终态；这说明本批次完整性良好，不表示服务延迟达标。
- 原来的 3 对重复复用同一确定性轨迹，提供运行间重复证据，没有覆盖独立业务样本或不同到达形态。

### 审查判断

| 重要性 | 观察、对解释的影响 | 最小补救 |
|---|---|---|
| 主要解释缺口 | E1 同时增加请求数、到达率和工作量，并改变长度构成。对“加入这批任务的整体影响”，增加工作量是干预组成部分；对“长度构成的独立作用”，这些联动变化无法分离 | 先补低强度混合场景，判断持续积压是否是唯一值得研究的条件；长度机制另设对照 |
| 主要解释缺口 | 长排空、后到请求等待增加与持续积压一致，但没有同请求的服务端分段 | 使用客户端未终态数与时间趋势判断是否仍积压；措辞限于观测一致，不把 TTFT 全称为引擎排队 |
| 重要限制 | 独立比较单位是整轮服务运行，效应重复单位是 3 个配对；共享队列内请求相互依赖 | 按轮列 P95 和配对差值，不把 1500 条请求当成 1500 次独立实验，不逐请求 bootstrap 制造精度 |
| 重要限制 | 三对顺序轮换只能部分减轻漂移；宿主竞争、温度和缓存不能视为完全相同 | 新旧数据分批呈现；新增同期基线、记录运行环境和轮间恢复条件 |
| 重要限制 | 当前统计脚本的 TTFT 分位数基于 completed 请求；旧批次全部完成，因此本次没有完成者筛选造成的遗漏 | 新实验同步列全体终态、首内容覆盖数；若有非完成者，限制完成者 P95 的解释 |
| 次要但需保留 | 业务标签预先固定，max_tokens 是上限，温度为 0 仍不保证相同实际长度；缓存也会变化 | 保留实际输入、缓存、输出、结束原因，不能事后挑选样本凑等工作量 |

允许的判断：在所用设备、引擎、模型、缓存与合成轨迹下，加入指定后台负载的条件重复出现明显更长的交互等待；在环境稳定等假设下，可讨论这批负载的整体影响。尚未证明长度异质性独立致因、内部软预算有效、KV 回收正确或跨设备普遍成立。原报告已经承认这些限制，本次不否定已完成的工程与描述性证据。

## 2. 最小补充实验卡：同期基线与低强度混合负载

### 问题、假设与判断幅度

研究问题：保持当前交互轨迹及后台请求生成规则，后台计划到达率由原来的 1 req/s 降为 0.1 req/s 后，相比同期交互独占，交互 TTFT P95 是否仍有实际值得关注的增加，同时是否没有明显持续积压？

待检验假设 H1：低强度混合场景在没有明显持续积压的运行中，仍出现可重复的交互 P95 损失。替代解释是原来巨大差异主要依赖持续积压，或这种稀疏后台场景下损失较小。**两者目前均未验证。**

建议将每对 `Δ=P95(L)−P95(C) ≥100 ms` 作为本次可行性筛选的实际关注幅度。100 ms 是人为预设的探索性工程门槛，相对旧基线约 35 ms 足以触发后续研究讨论，不是用户研究结论、正式 SLO 或显著性阈值。完整报告差值，不把门槛附近的结果硬分为有效/无效。

### 场景与固定项

新编号 C、L 用于本补充，避免覆盖原 E0/E1。

| 项目 | C：同期交互独占 | L：低强度混合 |
|---|---|---|
| 交互 | 原批次的 200 条完整交互轨迹 | 与 C 逐字段相同 |
| 交互到达 | 0、0.5、…、99.5 s | 相同 |
| 后台 | 0 条 | 固定 10 条，0.25、10.25、…、90.25 s |
| 后台选取 | 无 | 原 E1 轨迹中 B000、B010、…、B090；保留原 ID、prompt、参数和到达时刻，按编号确定，与结果无关 |
| 最大输出预算 | 200×64=12800 token | 交互 12800，后台 10×384=3840 token |
| 输入量 | 固定原交互 prompt 集 | 同交互集加固定后台子集；执行前记录分词总量，不虚填实际 token 数 |
| 采样、缓存 | temperature=0，默认前缀缓存，每轮全新服务和原来的两条固定预热 | 相同 |
| 服务 | 原引擎和模型完整 SHA；`-ngl 99 -c 4096 -np 2 -b 2048 -ub 512 --metrics` | 相同 |
| 容量 | 2 slot，各上下文 2048；逐请求检查输入 token+输出上限 | 相同 |

预计后台工作量明显低于原 E1，但**不能事先称 L 为“非过载”**。0.1 req/s 是有意大幅降负载的首个探针，不是由全程 token/s 反算的容量阈值。旧全程吞吐受场景、批处理和排空影响，不代表可直接复用的服务能力常数。

L 是原混合轨迹的确定性稀疏化，因而请求子集、缓存路径和实际输出总量会随之变化；它回答这项整体稀疏化干预的问题，不是对单纯到达率或长度的纯效应估计。交互与后台固定相位也限制其代表性，不推广为所有突发和随机到达负载。

### 重复与次序

- 最小矩阵为 **2 个场景×3 对=6 轮**，共 1230 条测量请求、另有 12 条预热。暂不新增强负载重跑。
- 冻结顺序：第 1 对 C→L，第 2 对 L→C，第 3 对 C→L；这是有限的顺序轮换，不声称完全平衡。每对尽量相邻执行，整个服务轮次作为比较单位。
- 复用原轨迹以减少设计改动，三对只衡量运行波动；不将三次称为独立工作负载采样，不据此给正式显著性结论。
- 同一供电与性能模式；每轮预热前采用相同的 60 s 空闲观察，记录 CPU/宿主进程、GPU 温度、显存和利用率。持续存在的其他 GPU 计算任务或无法确认前轮服务已退出时，暂停，不一边运行一边改变环境规则。
- 原来三对只作历史强负载参照，不与新增 C 拼接成同期随机对照，不将六对合并作统计检验。

### 窗口、计时、完整性和失败规则

沿用 100 s 测量窗口、最多 180 s 排空、180 s 单请求总超时。开放到达、无外部闸门；每条释放时刻等于计划时刻，迟发门槛仍为 50 ms。TTFT 仍取 TCP 建连后、写 HTTP 前至首个非空生成内容的客户端单调时钟差；连接等待计入迟发，不能混用旧 urllib 调用前边界。

完成、拒绝、超时、取消、失败、统一截止未完成六类互斥，合计等于计划数。每条独立 JSON、原始流式块、轨迹、环境、启动参数、种子、顺序、源码/模型/引擎摘要和退出码完整保留。统一截止不能延长以等待全部成功。

出现迟发>50 ms、版本不一致、缺文件、终态不闭合、上下文截断或分配异常时，该轮标为需复核；保留所有记录，暂停后续配对查原因。重跑使用新 run_id，并明确原配对受影响。**高时延、超时、拒绝或排空长本身不是删样理由**；它们是结果，只要测量可信就报告。

现有 `70_run_prestudy.py` / `80_analyze_prestudy.py` 固定原 E0/E1 矩阵和 3×(200+300) 断言，不能直接当作新协议的通用执行入口。将来获准执行时应另建版本化配置和适配入口，先验证 200/210 的计数、轨迹及输出口径；本轮不改脚本、不生成执行配置、不启动校准或服务。

## 3. 预先固定的分析与决策

主指标：每轮 200 条计划交互对应的 completed 样本 TTFT P95，采用现有排序后线性插值；每对给出 Δ，另报 P50。同步列出交互计划数、完成数、有首内容数、其他终态以及缺失原因，避免把 completed 的 P95 写成全体服务质量。

补充报告：已观测首内容（包括后来非完成者）的 TTFT 分布及其覆盖分母；无首内容者保留终态与截至时长，不赋值为 0。若交互存在非完成者，不能仅凭完成者 P95 宣称改善或满足 H1；先按完整终态判断结果是否足以解释。

后台仅 10 条/轮：报告每条从计划到达到终态的耗时和终态、完成者中位数与最大值。若附 P95，注明样本稀疏，不以其作主要决策。分别报告输入、缓存、新处理与实际输出 token、结束原因；缺失时列未知，不拿 max_tokens 代替实际值。

吞吐仍分为 100 s 窗口内完成请求/100 s，以及完成请求输出 token/从测量起点至最后客户端终态的时长（含排空）；非完成请求的已生成工作不在后者完整计量范围内，必须标注。无闸门的实际发送分母与计划数并列。

### 如何判断“没有明显持续积压”

只用客户端同一时钟重建 `N(t)=已实际发送数−已终态数`，在每个计划到达事件前取左极限值，避免把新到达请求当积压；以全部 `N(t)` 展示曲线。它包括在途生成和网络等待，不等于引擎 deferred 队列或 KV 占用。

建议冻结以下联合诊断，作为本次有限窗口的工作定义：

1. 每个后台到达前（10.25 至 90.25 s，共 9 个检查点），前一条后台和此前已发送交互均已终态，即 `N(t−)=0`。
2. 按交互计划到达划分四段 [0,25)、[25,50)、[50,75)、[75,100) s，各 50 条，列 TTFT P50/P95；最后一段 P50 不比第一段增加超过 100 ms。分段 P95 仅诊断，不替代全轮主指标。
3. 窗口后 10 s 内所有计划请求终态闭合，且没有非完成者。此为观察判据，统一最大排空仍保持 180 s。

这些阈值是本次预设建议，满足只支持“此 100 s 轨迹未见明显持续积压”，不证明长期稳态或接近容量边界。未满足仅说明暂不能归入该类，需要看曲线和终态解释，不能自动宣布引擎过载。

| 完整结果 | 允许的下一步 |
|---|---|
| 三对 L 均满足上述诊断，且三对 Δ 均≥100 ms | 得到无需明显持续积压也存在干扰的探索线索；支持继续讨论准入价值，但未识别长度独立效应 |
| L 满足诊断，但 Δ 较小、方向不一致或靠近门槛 | 当前低强度场景证据不足；保留结果，下一版可预先设计中间强度，不能反复加压直至出现“理想”结果 |
| L 仍持续积压或出现非完成终态 | 不宣称回答了无持续积压条件的问题；另立修订协议考虑 0.05 req/s，不在本轮临时调负载 |
| 测量或版本完整性未通过 | 修复工具与来源记录后另编号复验，暂不作性能分流 |

三对仅逐轮列结果、配对差值和范围，不报正式 p 值或用请求数构造窄置信区间。出现相反结果须同等保留；“本场景未见”不等于证明没有干扰。

## 4. 为什么先不增加其他场景

本次最小方案只补过载解释的缺口，不能替代长度对照。若论文仍要求“长度构成的独立影响”，下一步应另设计原方案中的 E3：保持后台请求数、到达点、输入模板/长度规则及预设输出总预算，改变长度分配的离散度，并平衡长任务的时间位置。先用独立校准数据确认实际长度操纵确实实现，正式数据不得事后筛选凑总量；等 token 也不保证等计算代价。

E2 会额外改变请求数与每请求开销；E4 服务端分段需要可靠 ID 和同钟计时；E5 外部闸门需同时评价后台等待、完成量和全部未完成。这些均可能有价值，但当前不必一起做。即使未来 E5 有收益，也不能据此宣称内部 C++ 软预算有效。

## 5. 机时、磁盘与停止边界

已验证旧批次六轮测量至最后终态合计约 966 s（16.1 min），不含启动、预热与轮间等待。它只用于资源估算，不用作新低强度场景的容量证明。

- 新方案测量与排空的协议上限为 `6×(100+180)=1680 s=28 min`；六次固定 60 s 观察另需 6 min。
- 低强度下若每轮约 100–110 s，预计测量 10–11 min；加观察、启动/预热和核对，建议预留 **30–45 min 机器窗口、1–2 h 人工准备与审查**。均为估算，启动异常时不保证完成。
- 将来执行时每轮服务就绪及两条预热合计最多等待 120 s，超限保留错误并停止；机器窗口到 60 min 不启动新轮，已启动轮按原统一截止收尾。故障不通过延长排空解决。
- 磁盘准备建议至少 1 GiB 新证据预算，另保留 1 GiB 系统余量；这不是实测输出大小。每轮前检查可用量，不足则不启动新轮。达到预算暂停新增轮次，保留已经生成的日志与原始档案，不清理旧数据腾空间。
- 首轮关键完整性失败即暂停。可信但不利的性能结果不触发“删掉再跑”；最大矩阵仍为 6 轮，不自动加入 E2–E5 或额外负载档。

所有新增批次只归入 prestudy/校准与开发证据，不用作未触碰的最终测试集。后续 P1 另冻结最终工作负载、种子、SLO、重复规模和参数搜索。

## 6. 可直接用于论文的当前措辞

> 在固定设备、模型及合成轨迹下，三次配对预实验中，加入指定后台负载的场景均出现更高的交互 TTFT P95。该场景同时增加了请求数及实际生成量，并出现较长排空，因此现有结果不能分离长度构成与负载强度的作用。我们据此提出低强度混合负载与同期交互独占的补充对照，以考察未见明显持续积压时是否仍存在值得关注的交互等待损失。补充实验尚未执行，现阶段未验证自研准入策略收益。

G0 仍需文献最近邻核验、研究范围、有效人时与完整后续机时评估及评审记录。本文只完成实验复审和最小补充设计，不构成 G0 通过或实验执行授权。
