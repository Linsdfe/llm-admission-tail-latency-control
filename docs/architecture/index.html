项目架构阅读指南 · 2026-10-22

让两类请求共享模型，研究如何减少交互等待

这个项目不训练新模型，而是计划在 llama.cpp 推理服务里增加一个 C++ 控制层：决定谁先进入执行、现在还能接多少工作、后台等太久时如何获得服务。

已有回放、测量、审计与归档工具；自研准入控制仍待实现。下面的目标设计解释“准备怎样做”，不表示已经获得性能提升。

先抓住三个问题

谁在使用系统？

交互请求希望尽快看到回答开头，后台任务需要最终得到处理。它们共享同一个模型实例和 GPU。

交互 / 后台是业务类别；输入和输出长度是另一组属性，不能直接画等号。

系统打算控制什么？

在模型执行之前控制请求的准入时机与候选顺序，并用完成后的真实长度更新软估计。

llama.cpp 继续负责模型计算和流式输出；不把此项目误读为重写推理引擎。

怎样判断有没有价值？

观察交互中较慢请求的首内容等待，同时检查吞吐、后台完成代价以及拒绝和失败。

保护交互不能只靠让后台永远等待；图中不使用实测收益数值。

第一次看项目时容易混淆的概念

准入与排队

请求到达不等于立即进入模型执行。准入决定何时允许执行；等待中的请求仍要被记录，并受期限和退出规则约束。

硬容量：能不能放得下？

按实际输入长度与最大允许输出保守预留逻辑容量，还要检查单序列上限和可用槽位。预测乐观也不能突破它。

软预算：现在是否太忙？

用未处理输入与预计剩余输出估计工作量；即使硬容量足够，也可暂缓接纳。它是成本近似，不是精确时延保证。

估计与在线校准

估计器预测生成长度；校准根据已完成样本补充正向误差余量。后续决策可以使用新余量，但不能偷看未来结果。

后台老化与保护

后台等待达到阈值后进入保护集合，为其腾出接纳机会；它仍须满足硬约束，不能保证任意过载下都在有限时间完成。

slot、prefill 与 decode

slot 是承载执行序列的位置；prefill 处理输入提示词；decode 逐步生成输出。核心计划使用固定 prefill 配置。

TTFT 与 P95

TTFT 是从实际发送到收到首个非空生成内容的时间。P95 是这类等待时间的第 95 百分位，用来描述较慢请求，不能当成最大值。

逻辑回收与显存释放

归还硬账本前必须确认执行停止、序列清理与槽位安全；逻辑容量释放不等于 GPU 显存立即返还操作系统。

一个便于理解的例子（示意，非实验数据）

某请求的实际输入是 100 token，允许最多生成 300 token。硬预留的基础量是 100 + 300 = 400 token，之后还需按分配粒度取整。即使估计只会生成 50 token，硬预留也不能因此缩成 150；这个估计只参与软工作量判断。
