## 第一步：打通可复核的原始推理链路（P0 起步）

**目标**：在现有 WSL2 环境下，使固定版本的原始引擎能加载一个可容纳模型、完成流式请求，并留下可重复运行的证据。先证明环境和测量路径可用，再开发调度策略。

依次完成以下任务；起步预计投入 6—8 人时，计入 P0 的 30 人时，不另加预算。遇到工具链或显存问题时登记实际投入并重新估算。

1. 在 WSL 中核对 GPU 可见性、编译器、CMake、CUDA、可用内存及磁盘；将命令、版本和时间记录到 `docs/environment.md`。现有报告中的配置是历史采集值，本轮运行仍需记录。
2. 在 `third_party/llama.cpp/` 获取引擎，选定并记录完整提交 SHA；按该提交自带文档构建，记录完整命令、构建开关和产物路径。首轮不修改引擎，也不在本阶段预定尚未核实的接口。
3. 选择并加载一个设备可容纳的 GGUF 模型；在环境记录中填写来源、许可证、文件 SHA256、量化及分词器信息。确定上下文、并行槽位、卸载与采样参数，出现容量不足时调整配置并保留原因。
4. 依次发送一条交互请求和一条后台请求，核对流式响应首个非空生成内容、结束原因和实际生成长度。业务类别独立于长度；原始引擎不支持类别字段时由客户端记录。
5. 依据固定提交定位接入、等待队列、slot 分配、prefill/decode、取消和清理路径，填写 `docs/source-map.md`。记录准确文件和符号，不凭名称推测行为。
6. 在 `results/raw/prestudy/<run_id>/` 保存本轮环境、完整启动命令、服务端日志和请求记录；将 `configs/run-manifest.template.json` 复制为该目录下的 `manifest.json` 并填写。未知字段保留 null 并说明原因。

**预期成果**：环境记录、固定引擎与模型摘要、可重放的构建/启动/请求命令、两条真实请求的流式记录、初版源码定位表。

**完成判据**：同一配置重启服务后两类请求均可完成；能够从记录识别首个生成内容与终态；固定版本和配置足以供自己重新构建。两条请求仅用于冒烟核对，不构成尾延迟结论。未满足时先解决构建、容量或测量问题。

**第一步执行记录（2026-10-19）**：第 1—6 项已完成并留证。

- 环境：`docs/environment.md`（实测值与原始输出路径）；原始输出 `results/raw/prestudy/2026-10-19-env-check/`。
- 引擎：llama.cpp **v0.7.0**，SHA `620d2225cc436ab0b001e3200e590e3b286ef9ab`；克隆记录 `results/raw/prestudy/2026-10-19-build/clone-record.md`；CUDA 构建 12.8 min，产物 `build/bin/llama-server`、`llama-cli`、`llama-bench`。
- 模型：Qwen2.5-1.5B-Instruct **Q4_K_M**，SHA256 `6a1a2eb6…e434e9407e`（与 HF 发布值一致）。
- 冒烟（正式证据）：脚本化 v2，`results/raw/prestudy/2026-10-19-smoke-v2/`。2 条预热 + 3 条测量请求（交互、同 prompt 缓存探针、后台），全部 `finish_reason=stop`、`truncated=0`。客户端逐块计时结果：交互 TTFT **26.48 ms**（`prompt_ms` 24.37，交付开销 2.12 ms）、同 prompt 命中缓存 TTFT **11.87 ms**（`cache_n=41/prompt_n=1`）、后台 TTFT **30.36 ms** 后持续生成 3.22 s（312 token，97.48 t/s）；逐 token 间隔 p50≈10 ms、p95 12—15 ms。手工 curl 的 v1（`2026-10-19-smoke/`）存在 `ttfb` 误作 TTFT、SSE 文件被覆盖两处缺陷，保留作“无预热冷态”对照，不作为正式证据。
- 关键协议结论：运行内受控对照显示预热第 1 次 TTFT 82.06 ms → 第 2 次 26.87 ms 后进入稳态（26—30 ms），因此实验固定 ≥2 条预热且不计入样本。跨运行比较（v1 首请求 prompt 处理 277.79 ms vs v2 58.09 ms）为混合因素（图/算子首次调用、GPU 时钟、页缓存），未受控分离，不作定量结论；预热效果的受控测量放在 P3 基线阶段。
- 源码定位：`docs/source-map.md`（7 条链路到文件:行号，15 个接入点候选）。
- 遗留缺口：并发/排队与开放到达尚未覆盖（v2 全程 `requests_deferred=0`、`n_busy_slots_per_decode=1`）；排队时长需在到达/出队/首 token 三处插桩。两项在第二步回放器中补齐。

**第二步启动清单（下次会话照此执行）**

1. 同步到 WSL（Windows 工作区的改动不会自动进入 WSL 副本）：运行 `scripts/ops/sync.sh`（单向 Windows → WSL，同步 `docs/ daily/ configs/ scripts/ src/ include/ tests/ data/ tools/ patches/` 与根目录文件，并清理 `__pycache__`；原始证据 `results/raw` 只存 Windows 工作区，不同步）。
2. 记录运行前基线：`nvidia-smi`（显存占用）、确认 VMware 与浏览器已关闭；运行前先跑 `scripts/replay/00_env_check.sh`，再用 `scripts/replay/50_run_all.sh` 一键起服务、预热、测量、停服务。
3. 实现 `scripts/replay/` 回放器（以 `stream_client.py` 的逐块计时为内核），必须包含：计划到达表与开放到达、客户端单调时钟、**逐块时间戳（首个非空内容 = TTFT）**、每条请求独立文件（不得覆盖）、固定 ≥2 条预热与每重复前重置状态、终态互斥分类（完成/拒绝/超时/取消/失败/未完成）。
4. 先跑 10 条小轨迹核对（ID、发送滞后、首内容、终态、排空）→ 通过后再跑 E0（200 条交互 × 3 次重复）与 E1（同轨迹 + 约 100 条后台）。
5. 产物落到 `results/raw/prestudy/<run_id>/`：轨迹、客户端日志、服务端日志、`manifest.json`；报告交互 P50/P95、配对 Δ、终态分布与后台代价。
6. 每次工作结束后在 `daily/<YYYYMMDD>/README.md`（按 `daily/TEMPLATE.md`）记录当天任务、产出、数据、问题与下一步，并在 `daily/README.md` 索引表中追加一行。

## 基础目录与职责

| 路径 | 用途 |
|---|---|
| `docs/` | 执行计划、环境、源码定位、设计决策与阶段报告；根目录三份研究文档继续作为依据 |
| `src/{admission,estimation,fairness,runtime,observability}/` | C++ 准入、长度估计/校准、公平保护、引擎适配/回收、事件观测实现 |
| `include/llm_control/` | 项目公开 C++ 接口；待状态和接入设计确定后添加 |
| `configs/` | 可追踪的引擎、策略、回放配置与运行清单模板；模板不直接用于正式实验 |
| `scripts/{replay,analysis}/` | 负载生成/回放与终态、指标、区间、图表分析 |
| `tests/{unit,integration}/` | 容量/校准/老化单元测试，以及真实引擎生命周期与测量集成测试 |
| `data/{workloads,calibration,development,test}/` | 轨迹定义与校准、开发、最终测试数据；最终测试不参与调参 |
| `results/{raw,processed,figures}/` | 按 run_id 保存原始证据、派生指标、图表；原始数据只追加 |
| `third_party/` | 固定版本 llama.cpp 的本地检出与版本说明 |
| `models/` | 本地模型、分词器和摘要；大文件不提交 |
| `patches/` | 相对于固定引擎提交的系统补丁与应用说明 |
| `tools/` | 现有 Markdown/Word 同步与排版工具 |

`CMakeLists.txt` 提供不依赖推理引擎的目录配置入口；当前无可执行程序。`build/` 是未来生成目录，已忽略。后续在 WSL 内构建；需要 Linux 文件系统性能时，可将仓库克隆到 WSL 的 `~/projects/`，原始实验中记录实际路径。

## 执行纪律

- 硬容量按实际输入长度和明确的最大输出长度完整预留，预测仅参与软决策；检查与扣减保持原子控制路径。
- 回收必须在执行停止、序列清理和槽位安全复用后一次性归还预算。
- 客户端使用同一单调时钟计算时间差；跨时钟未验证时不相减。
- 完成、拒绝、超时、取消、失败、截止未完成互斥且总数闭合；有闸门的实验跟踪尚未释放请求。
- 冻结引擎和模型后再作对照，变更版本须重建基线；原始日志不覆盖，修复分析保留旧结果与原因。
