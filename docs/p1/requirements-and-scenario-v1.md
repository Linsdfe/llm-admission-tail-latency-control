# P1 需求与场景草案 v1

编制日期：2026-10-24（Asia/Shanghai）。状态：草案，G1 待审。用户已明确 G0 通过，并授权开始下一阶段；这不代填导师或学院的审核意见。本文件记录 P1 拟定要求，不表示下述机制已经实现或正式实验已经完成。

**接下来要回答：同样估计请求长度、同样排队和保护后台时，根据历史误差调整保险余量的 M，比使用固定余量的 B3，多带来多少收益，又增加多少代价？**

## 1. 谁用这个系统，想解决什么问题

假设一台个人电脑同时做两件事：用户随时发来简短问题，希望尽快看到第一段回答；电脑还在批量处理一些较长的离线文本，希望后台持续推进。两类请求共用一个模型和一张显卡。

用户故事如下。

- 我正在聊天，希望后台忙时也能尽快开始回答，并能看见请求是否仍在等待。
- 我提交了后台批任务，允许它比聊天慢，但不希望系统一直只处理聊天，让后台永远排不到。
- 我取消了请求，希望系统停止执行，并在确认清理后归还占用，后续请求能正常运行。
- 我做实验，需要查出每条请求在哪里等、为什么放行或延后、最终怎样结束，不能只看成功请求。

目前没有真实生产流量或正式业务 SLO。下列场景是公开说明的合成工程使用假设，不能代表所有聊天产品、模型或硬件。

P0 已观察到取舍：最新突发负载下，简单优先的聊天 P95 总等待约 2.79—2.83 秒；后台并发上限为 1 时约 0.053—0.061 秒，但后台完成 P95 增加约 103%—139%。这组探索结果支持研究等待与后台代价的取舍，不证明 M 有收益，也不作为最终测试结果。

## 2. 唯一主场景与两个边界

| 场景标识 | 计划到达方式 | 本场景要检查什么 |
|---|---|---|
| `main_bursty_mixed`，唯一主场景 | 100 秒内 200 条聊天，每 0.5 秒一条；30 条后台，每 10 秒提交一批 3 条，批内间隔 50 毫秒，共 10 批 | 后台成批到来时，聊天等待和后台进度能否兼顾 |
| `boundary_steady`，边界一 | 聊天不变；同样 30 条后台均匀到达 | 后台不成批时，简单规则是否已经足够，复杂方法是否徒增代价 |
| `boundary_sparse`，边界二 | 聊天不变；10 条后台，每 10 秒一条 | 后台很少时，额外控制是否仍有必要 |

这些是草案到达结构。首批相位、固定抖动及每条到达时间由[实验协议草案](experiment-protocol-draft-v1.md)生成清单，并在 G1 冻结。100 秒是发送窗口，排空另计。

主场景选择突发，是因为 P0 已显示明确服务取舍，且“集中提交离线批任务”能解释这种到达方式。开发阶段须核对总工作量、队列增长和排空，说明负载是否可服务；不能以 M 更容易获胜作为选负载或改参数的条件。若持续过载，应先修改并重新登记场景，再冻结最终测试，不把过载包装成正常服务。

正式请求采用新内容、新模板家族和新种子。P0 四批已看数据只作开发依据。校准、开发、最终测试按内容与模板家族隔离，不能只改请求编号；最终模板、内容、到达清单及种子在测试前保存哈希。完整划分见实验协议。

## 3. 固定环境与输入输出约定

| 项目 | 拟定要求 |
|---|---|
| 设备与模型 | 现有 RTX 3050 Ti Laptop 4 GiB，Qwen2.5-1.5B-Instruct Q4_K_M；固定模型哈希 |
| 执行方式 | 单实例、2 个执行位置（slot）、每位置上下文 2048 token，非主动抢占 |
| 固定执行参数 | 核心策略共用固定 prefill/decode 设置、采样和输出上限规则，具体值按协议冻结 |
| 请求必要字段 | 全局唯一 `request_id`、类别 `interactive/background`、提示内容、正整数 `max_output_tokens`、统一请求期限；运行清单另存计划到达时间 |
| 请求限制 | 只接入单序列文本生成，`n=1`；不接图像、多候选生成或无限输出请求 |
| 输入长度 | 用实际分词结果计算，包含模板与特殊 token；聊天草案范围 32—256 token，后台 128—1024 token |
| 输出与采样 | 聊天输出上限 64 token，后台 384 token；temperature=0，自然 EOS 与触顶分别记录，完整采样配置按协议冻结 |
| 输出记录 | 流式内容、实际输出 token、停止原因、终态；到达输出上限也要如实记录 |
| 外部结果 | 明确返回完成、容量拒绝、取消、超时或错误；统一截止仍未结束的请求单列 |

每类输入范围、输出上限和采样配置均为草案值，详见实验协议。不同策略对同一请求使用相同提示、上限和计划到达时间；不能为了某策略达标而缩短回答、减少后台任务或增加拒绝。

## 4. 先守硬边界，再决定是否值得现在放行

硬容量回答“最多能装多少”。每条请求按实际输入加最大输出保守预留，预测值不能减小这笔额度。软工作量回答“现在放进来会有多忙”，只用于延后或选择请求。

- 单请求草案检查为 `实际输入 token + max_output_tokens + 1 <= 2048`，至少留出 1 token 边缘余地。P0 中 2047 输入加 1 输出虽返回内容，但会触发容量停止，不能当作完整预算安全证明。
- 正式硬预留还要按引擎分配粒度向上取整。G2 须核实粒度、安全余量及真实模板编码，再冻结单位置和总 `C_safe`；不能把上述算式当成已完成的硬账本。
- 全部活跃请求的取整预留合计不超过 `C_safe`，活跃数不超过 2，每个请求也满足单序列限制。共享前缀或预测较短不能抵扣保守预留。
- 永久装不下或参数不支持的请求明确拒绝。只是当前容量不足的请求等待；超出统一期限后超时，不能记成容量拒绝。
- 回收顺序为确认执行停止、清理序列、确认位置可复用、一次性归还账本。客户端超时或关闭连接不等于服务器已经释放。

逻辑硬账本约束上下文容量，不保证其他进程、模型权重或工作区不会耗尽物理显存。实际显存、容量错误和进程退出仍须观测。

M 与 B3 共用冻结的点估计器，预测“给定输出上限下实际执行的生成长度”。M 只读取当前时刻已完成请求的正向预测误差，按登记规则更新余量；B3 使用开发集选定并冻结的固定余量。失败、取消、超时和未完成不能填成零长度校准样本。

样本不足时，M 使用事先登记的固定回退。反馈延迟、每桶样本量、余量、预测超出和输出触顶必须记录。软预算不能修改用户上限、放宽硬容量或承诺普遍延迟保证。

## 5. 后台怎样得到服务

后台等待达到固定阈值后进入保护集合。系统暂停会持续占用其所需容量的新准入；现有请求结束、硬容量足够时，先放行等待最久的可容纳保护请求。平局用固定规则打破。

空系统中的单个可容纳请求，以及受保护后台，按预定规则绕过软预算等待；它们仍不能绕过硬容量。后台接纳后获得正常 prefill 和 decode 机会。保护阈值、解除条件和优先级由 G2 写成伪代码，并在最终测试前冻结。

后台保护的前提是负载可服务、现有请求能够结束、单请求装得下。任意过载下不承诺有限等待上界。P0 的“最多运行 1 条后台”是已测简单原型，不自动等同于正式固定服务配额，也不能代替上述保护机制验收。

## 6. 需要哪些对照

编号沿用开题原义，不能因为已有某段代码就替换定义。

| 编号 | 正式含义 | 用来回答什么 |
|---|---|---|
| B0 | 原始引擎，单列源码与运行配置 | 实际部署参考 |
| B1 | 公共硬守卫加原始顺序 | 组合方法相对基本系统的整体收益 |
| B2-P | 交互优先 | 简单优先是否已经足够 |
| B2-Q | 固定服务配额 | 固定配额是否已经足够，不能改称固定并发上限 |
| B3 | 同估计器、候选顺序、后台保护，使用固定软余量 | M 的核心增量对照 |
| B4 | 同预测器的长度排序 | 长度排序和公平代价 |
| M | 在线误差余量、软准入、后台保护组合 | 在线更新是否值得增加成本 |
| NN | 至少一种最近邻规则的明确适配 | 与接近的已有方法比较，来源与适配差异待 G1 选定 |
| M 去校准 | 余量置零，其余不变 | 误差余量的作用，不等同于固定非零余量 B3 |
| M 去老化 | 关闭后台老化与相应保护，其余不变 | 后台保护的作用及代价 |
| S_cap1，辅助强简单对照 | 公共硬守卫、交互优先与同老化，后台最多同时运行 1 条，老化不绕过此上限 | 检查已在 P0 显示明显收益与代价的简单上限，避免遗漏强对照；不等同于 B2-Q |

B1—B4、M 和适配 NN 共用硬守卫、回收、观测及可比执行设置。需要预测的策略共用点估计器和可取得的信息。M/B3 的候选顺序、分桶、回退、软成本、预算、保护和参数搜索预算逐项对齐，关键差别只留在余量是否在线更新。

B0 是独立原始引擎参考；B1 的观测和共同正确性修改须列清，不能把这些差异全部归为硬守卫。P0 最新 `original` 含共同取消修复，不冒称未经修改的 B0。NN 与已有配置确实等价时可以共用运行，但保留映射，不虚增独立结果。

主场景保留 10 个核心配置，再加 S_cap1 辅助配置，共 11 个，等价配置可按登记规则去重。S_cap1 的公共硬守卫与其他策略一致；它不能直接借用 P0 的性能结果替代正式测试。

边界保留 B1、B3、开发阶段锁定的简单规则 S、M、NN。S 的开发候选包含 S_cap1，按预定联合约束选择，不能看最终结果挑较弱对手；即使 S_cap1 未被选为边界 S，主场景仍保留它的辅助结果。矩阵和去重规则见[矩阵与预算草案](experiment-matrix-and-budget-v1.md)。

## 7. 怎样计时、对账和验收

聊天的主要等待按“计划到达至首段非空生成内容”计，包含客户端迟发及外部等待；另报实际发送至首段内容的 TTFT。不能把响应头或空 SSE 块当首段回答，也不能混用两种时间起点。

回放器使用客户端单调时钟记录计划、实际发送、首内容和结束。服务端用本进程单调时钟记录接收、准入、执行与释放。只能比较同一时钟域的差值；跨进程用请求 ID 关联，不能直接相减未经校准的时钟。

请求的系统总期限暂定为计划到达后 180 秒，外部等待计入；HTTP/传输兜底另设 360 秒，全轮截止为零点后 280 秒，以更早的有效期限为准。不能把传输超时或流式数据间隔当作新的系统期限。启动健康检查 120 秒与两条预热最多 60 秒分开计，预热不入性能与校准反馈。

每个计划请求恰好落入以下六种外部终态之一。截止时尚未发出也不能删除。

| 终态 | 含义 |
|---|---|
| `completed` | 正常结束，保留 EOS、达到输出上限等原因 |
| `rejected` | 明确拒绝，如永久容量不足、参数不支持 |
| `cancelled` | 客户端按约定取消；服务端是否停止、何时回收另核对 |
| `timeout` | 达到统一请求时限，服务端回收另核对 |
| `failed` | 连接、服务或执行错误，有错误原因 |
| `unfinished` | 统一截止仍未结束，包含未发出或仍等待/执行的请求 |

最终实现字段须与回放器现有字段建立显式映射，不能因命名不同丢请求。六类合计等于计划总数；每个身份唯一，终态互斥。外部终态与内部资源回收是两套记录，取消/完成竞争只能归还一次。

最低日志字段包含请求身份、类别、策略、输入/缓存/输出 token、上述时序与终态。每个决策点还要记录候选、硬允许或阻塞原因、预留与占用前后值、软成本/预算/余量、保护状态及决定；误差更新记录样本身份、完成时刻与反馈进入时刻。不能仅用全部到达数作“软规则介入比例”的分母，须单列硬约束允许的决策点。

| 需求 | 可检查要求 | 验收证据与阶段 |
|---|---|---|
| R01 两类接入与身份 | 必要字段校验明确；重复 ID 不重复执行；计划、接收、终态能关联 | 小轨迹与重复请求测试，逐请求计数；P3 / E2 |
| R02 长度估计和软决策 | 相同状态下能解释预测、余量、硬允许/阻塞和软放行/延后；只读已完成反馈 | 决策日志、冷启动/误差扰动/零余量测试；G2 给状态，G3 核介入，P5 比 M/B3 |
| R03 硬容量与回收 | 取整预留、单序列和位置约束均成立；取消/超时/失败后一次性归还 | 容量边界、并发与竞争测试、真实释放事件；P3—P5 / E3 |
| R04 后台保护 | 保护触发后新准入不持续抢占所需容量；可容纳后台最终得到执行机会 | 人工轨迹、服务事件、等待/完成代价、去老化；P3—P5 / E6 |
| R05 可信时序与导出 | 时钟域明确，首内容定义正确，全部终态闭合；窗口与全程分母分开 | 注入已知等待的小轨迹、迟发校准、原始事件复算；P3 / E5 |
| R06 切换与复现 | 同轨迹可切换全部策略；源码、模型、参数、数据和分析均能定位 | 文件哈希、命令与环境、至少一组重跑、图表再生成；P3—P5 / E4、E7 |
| R07 收益和代价联合评价 | M/B3 核心比较完整；M/B1、简单规则、NN、消融不缺；不利结果照报 | 按独立运行报告延迟差、后台完成、速率、全部终态、开销与不确定性；P5 / E1—E7 |
| R08 动态 prefill | 默认不纳入核心和正式矩阵 | 新增须另登记理由、预算、固定预算消融和验收，不随 P1 自动开启 |

P95 指指定总体第 95 百分位。算法、失败处理与最小样本要求在协议冻结；不能只报完成者的漂亮延迟。共享队列的请求有依赖，独立单位是运行，不把几千条请求当成几千次独立重复。

## 8. G1 前还要定下什么

聊天等待 1 秒、至少 100 毫秒且 15% 改善、整体速率下降不超过 5%、后台 P95 增加不超过 20%，均来自探索或待论证的工程目标。它们不是已确认的业务需求，也不自动成为 M/B3 的最终判定线。G1 要分别冻结绝对服务目标、M/B3 最小有用差异、M/B1 整体目标及各项代价容限。

| 待定字段 | 定下来需要什么 | 草案期间怎样处理 |
|---|---|---|
| 业务目标与代价 | 用户认可合成使用假设及等待/后台取舍理由 | 保留候选值，不按结果调门槛 |
| NN 规则与适配 | 原文、所需信息、同条件可比范围、适配成本 | 保留独立 NN 名额，不宣称创新或已复现 |
| 输入/输出、分桶、搜索和划分 | 协议、内容清单、开发校准与预定搜索预算 | 新最终内容暂不执行，不读取未来测试反馈调参 |
| 工时与机时记录 | 按用户要求正常推进，成果完成后由本人补记人工工时 | 人工未知不阻塞当前或 G1，不再索要时间表；自动机时照实记录，不把旧 250 人时初估填成实际投入 |
| 重复与机时 | 独立运行波动、精度要求、完整周转和排空成本 | 以预算草案估算，超预算先减扩展和边界，不删强对照 |

G1 通过后再冻结协议版本。G2 固定设计与可介入状态，G3 用最小原型核对容量、回收和真实软决策机会；未发现可解释介入空间时先复核并收窄命题，不直接堆完整算法。M 的实际增量价值留给后续公平实验，负面和不确定结果同样保留。
