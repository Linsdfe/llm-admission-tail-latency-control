## 目前的具体方案

采用单卡、单模型、两执行位置的合成工程场景。主场景暂定100秒内200条聊天，后台30条、每10秒集中到达3条。平缓后台和稀疏后台作为边界。选择依据是P0已观察到聊天等待与后台完成之间的取舍，尚未验证在线余量是否占优。

暂用聊天P95不超过1秒、至少改善100毫秒且15%、后台P95增幅不超过20%、全程输出速率损失不超过5%作为工程目标草案。这里P95指约95%的请求不超过的时间；正式主指标从计划到达算到首段回答，实际发送后等待另报。

在线余量和固定余量共用估计器、候选顺序、后台保护、硬容量和执行设置。两者的关键差别是余量是否在线更新。对照仍保留原始引擎、公共硬守卫、简单优先、配额、长度排序、最近邻和必要消融。

## P1接着完成什么

1. 实际长度、短窗口负载和扩样已核对；不把100秒无长积压说成长稳态。先修订提示与任务定义，检查回答完成情况；改变任务或预算后另测负载。
2. 锁定提示模板家族、长度分桶与三个集合的划分规则。最终测试数据尚未生成或查看。
3. QBA候选分界修订为目标加权64，已验证不再全短但与I/B重合；按补充v2核对实际顺序和提拔，再完成参数及简单规则S的选择准则，不按结果调弱对照。
4. 用开发期波动确定最终独立重复规模，锁定正式比较的统计方案。每配置5次只作起步成本估算，不代表证据充分。
5. 自动执行时间随日志保存，人工工时按用户指示成果完成后补；不以此阻塞推进。按机器成本核对次级场景范围。
6. 逐项完成G1检查，形成新版本冻结清单，随后按原计划进入设计阶段。

缺少的场景验证与参数信息会留在草案和G1表中。用户已要求工时不阻塞推进，人工记录留待成果后补。本次P1启动并未自动通过G1。
