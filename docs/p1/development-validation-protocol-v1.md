# P1开发验证执行协议 v1

编制日期：2026-10-24，Asia/Shanghai。用户已要求直接写代码、在WSL测试、记录分析、归档并推送GitHub。本协议在本批GPU采集前落盘，运行时保存本文件和执行源码快照与SHA；不改P0记录或开题正文。

## 1. 本轮回答什么

检查P1新场景是否能按方案生成和运行：实际输入含模板后是否合规，自然生成实际多长，客户端是否按计划发送、完整记账，突发/平缓/稀疏条件下是否出现短窗口积压。结果用于修订开发方案，不用于证明在线算法获胜、最终SLO达标或长期稳态。

只用现有最终修改引擎的原始选择路径，命名`prototype_original_order`。该引擎含共同取消正确性修复；没有正式公共硬账本，不能标成未经修改的B0或正式B1。本轮不实现或比较M/B3，不启动11配置正式矩阵。G0已由用户通过，G1尚未冻结。

## 2. 固定环境与提示来源

- 现有WSL Ubuntu-24.04、RTX 3050 Ti Laptop 4GiB、Qwen2.5-1.5B-Instruct Q4_K_M。
- 最终background-cap-v1引擎基底`620d2225cc436ab0b001e3200e590e3b286ef9ab`，运行库清单与既有最终探针对照，模型SHA为`6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`。
- 每轮新启原始顺序进程，2个slot、每slot2048上下文；`-ngl 99 -c 4096 -np 2 -b 2048 -ub 512 --metrics`，mode0、cap0、aging5000ms。
- 项目原创合成中文提示，校准与开发用不同模板家族。显式Qwen ChatML文本走原生`/completion`，不再套聊天模板。temperature0、cache_prompt=true、ignore_eos=false、I上限64/B上限384，自然结束和触顶分别记录。
- 输入核长用`/tokenize`，明确`add_special=true,parse_special=true`，与固定引擎的原生输入路径一致。I目标实际输入32至256，B128至1024；每类预定三个输入桶见工作负载配置。只按实际输入长度选满足桶的首个候选，不根据生成速度、拥堵或策略输赢筛选提示。
- 单请求实际输入＋最大输出＋1≤2048。真实响应再核`tokens_evaluated = timings.prompt_n + timings.cache_n = 冻结输入长度`。顶层`tokens_cached`是执行后序列字段，不当成输入前缀缓存。

## 3. 固定矩阵与顺序

校准seed11001，24条（12I、12B）串行执行，检查输入/输出分布、结束原因和记录链。这24条不足以训练或冻结正式估计器，不用它们声称预测精度达标。

开发提示seed21001、21002、21003，各生成200I与30B。每个重复的主/平缓场景共用完全相同内容和输出上限，仅改到达；稀疏取同批B索引0、3、…、27，共10条。

| 场景 | 100秒内计划到达 | 每重复测量数 |
|---|---|---:|
| main_bursty_mixed | I在0.5k秒；B在10g+0.25+0.05j秒，g=0..9,j=0..2 | 230 |
| boundary_steady | I不变；B在0.25+10k/3秒，k=0..29 | 230 |
| boundary_sparse | I不变；B在0.25+10k秒，k=0..9 | 210 |

执行次序：重复1主/平缓/稀疏，重复2平缓/稀疏/主，重复3稀疏/主/平缓，平衡每种场景的块内位置。不同重复换内容seed。共9轮、2010条开发测量；另24校准、20预热（准备服务2条、每轮2条），按实际记录单列。全局身份为批次/运行/req_id，跨场景同内容用content_id关联。

先用一个准备服务完成token化、两条预热和24条校准，再关闭。9轮各重启并预热，不沿用准备服务的KV。最终测试集合明确拒绝生成、未读取、未执行。不是把P0旧请求换ID。

## 4. 时限、失败与采集

新开发回放器保存异步串行写盘模式，避免写盘阻塞发送。每个请求系统期限为计划到达＋180秒，HTTP传输兜底为实际发送＋360秒，统一截止为轮起点＋280秒，较早者决定终态；客户端期限不等于服务器已回收。校准每条单独的短回放使用45秒请求期限及45秒排空，预热使用10秒期限，均单列不参与100秒性能统计。

六终态互斥并包含所有计划到达。结构化400 `exceed_context_size_error`记容量拒绝，其他400保留原错误并记failed；所有HTTP状态/响应原文保留。已出现首内容后超时仍保留首内容；没有最终生成计数则output_tokens=null、known=false，不填零、不用字符或SSE块顶替。

保存完整提示/到达表、每次token化的请求和响应、逐请求流式记录/结果、原生最终对象和timings、环境、完整启动命令、props、slots、metrics、GPU每秒样本、服务日志/退出码、源码/运行库/模型前后指纹。CPU/GPU竞争与温度如实记录。每轮开始固定空闲15秒并记录温度，不为某个结果挑温度或删轮次。

停止发送后的服务器恢复宽限单列，使用CAP真实启动/释放重建活动slot和后台数，不以客户端end猜释放。最终metrics处理/等待数归零，slot空闲， own进程正常退出。对性能超时、不利排空或没有干扰保留原样；计数、来源、容量或迟发门禁失败则暂停后续，修正时新版本、新目录并保留失败。

## 5. 分析规则

按轮、按类报告输入/输出min、P50、P95、max、实际缓存、触顶/EOS、六终态、首内容覆盖、聊天TTFT及计划至首内容P50/P95、后台完成P95/最大等待、发送迟发、100秒仍在途和排空。每10秒给到达/完成/剩余请求数，并结合服务器排队与执行事件检查积压，前后10条/秒段只作描述。

P95沿用type7线性插值。独立重复单位为整轮；三次用于开发波动观察，不作正式显著性、等效或M/B3样本规模定论。主/平缓只比较同重复；稀疏同时减少工作量，不单独识别长度原因。

全程速率分母固定`max(100,最后测量终态秒数)`；写盘和恢复宽限不混入。输出计数缺失时只报已核下界及known/missing，不声称全体速率可识别或联合达标。窗口内准确输出token若没有逐token来源则记未知，不用字符估数。完整完成者延迟不代替所有到达结果；终态与不可估情况并列。

## 6. 预算与版本保留
