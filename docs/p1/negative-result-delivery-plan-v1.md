# M没有额外收益时的交付与判读规则

2026-10-26编制，G1候选v3的组成部分。它是后续计划，不是已经测出的论文结论；不改题、不把简单规则或QBA包装成原创。

## 不依赖M获胜的交付

|交付|最低验收证据|阶段|
|---|---|---|
|可运行C++控制系统|接入、队列、最大输出硬预留、软准入、老化、启动/撤销/释放；同一测量链|G2设计，G3实现与异常验收|
|完整生命周期|六终态闭合，取消/超时后确认回收，重复释放防护、容量超界拒绝与同服务恢复|G3正确性测试|
|公平比较|M/B3同预测、同公开语法下限、同容量、成本、顺序、老化和开发信息；B3包含0余量强候选|G3合同核对，G4参数冻结|
|实证数据|同轨迹配对、全部终态、首内容/后台完成/全程速率/正确完成、逐块区间，固定20块|G5按预定矩阵采集；仅证明等价的别名去重|
|方法成本|决策CPU耗时、进程资源、状态字节、分词准备与缓存代价、改动规模分别报告|G3/G5；不给未记录开发人时编数|
|可核对成果|代码/配置/数据来源/全部失败/分析/哈希/重现命令与日期包，版本和最终访问日志|各阶段留证，G5冻结，G6交付|

系统正确性是交付前提。即使性能好，若硬容量或回收不成立，不能宣称系统完成。预测/算法结果不保证资料答案正确，质量始终另报。导师/学院对系统实现型本科毕设的要求仍需其正式意见。

## 不把“没显著变好”直接写成“没有用”

正式比较沿G1候选的20配对块、预先登记的同时区间与五项工程线。M/B3是核心；M/B1另完整报告，不能把两比较的收益/代价拼接。

1. **支持满足预设要求**：聊天绝对/相对改善区间下限分别≥100ms/15%，M首内容P95区间上限≤1000ms，后台/速率代价区间上限≤20%/5%。
2. **排除预设幅度收益**：至少一个改善指标区间上限仍低于100ms或15%。允许说“本范围内不足以达到预设幅度”，不能推广成算法普遍无效，也不是全体性能等效。
3. **成本明确超线**：至少一个代价区间下限已超过20%或5%。允许说“在该条件下代价超过预设线”。仅上限超线而下限未超时，仍属不确定，不能假装成本超线已被证明。
4. **证据不足**：区间跨判定线、过宽、指标不可识别/输出计数缺失或其他联合条件未确认。照实报告不确定性，不临时追加最终样本、不换主指标、不调最终参数。

这些状态可能并存，例如“排除预设幅度收益且代价超线”。完整列出各端点，不强压成一个胜负分数。不同请求共享队列，只对整块效果推断；相同观测轨迹不等于全部状态下策略等价。

## 当M/B3作用很小或实测没有触发

G3在已登记开发数据上核对：每次方法余量、公共下限是否吸收余量、选择/等待原因、空系统/老化绕过、硬容量结果与实际启动。先检查规则确实实现且测试能触发差异；故障修复保留旧版本和完整重跑块。

如果实现正确而本负载没有触发差异，写清“本负载未激活所研究的机制”，保留开发负面记录。不得临时加噪声、删掉公开上界、缩短后台或弱化B3来追M优势。仅在合同和实现能证明两个配置完全相同、可作别名时合并运行；只在几个开发轨迹中相同不能据此删掉真实不同的方法或取消不利正式对照。已登记正式比较仍按方案执行，除非用户评审明确修改研究范围并另立版本。

## 论文怎样写到收尾

第1章明确单卡混合请求的等待/后台代价问题及工程假设；第2章交代已有方法与本项目适配差异；第3章写容量、生命周期和控制接口设计；第4章写C++实现与正确性证据；第5章完整呈现简单规则、B3/M、最近邻、消融及方法成本；第6章按上面的四类证据状态说明适用范围、机制没有触发或收益不足的原因和限制。

没有M增益时，可成立的贡献是“实现并验证一套可追溯的控制系统，在已测试设备、模型、受限输出格式和到达条件下，量化更复杂控制带来的收益和代价”。不得写“证明所有场景简单调度最优”或“找到通用最小复杂度”。不以增加代码量、实验数量或制造新名词替代贡献。
