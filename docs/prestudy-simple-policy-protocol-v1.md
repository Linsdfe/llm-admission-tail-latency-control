## 1. 本轮只回答什么

在固定单 GPU、单模型、两个 slot 下，比较原始队列路径与“交互优先、后台等久后晋升”简单规则，观察它在预先固定的中间强度平稳与同总量突发条件下，能否改善交互等待，以及后台和吞吐付出什么代价。

研究对象是合成工程场景，不声称代表真实生产流量。后台率 0.3 req/s 事前选在历史 0.1 与 1.0 req/s 之间；这不预先保证可服务或无积压。固定同一组请求和预算，变化只有到达形状及策略。历史 E0/E1、C/L 只作背景，不代替本次同期对照。

三对配对运行是效应重复单位；共享队列的 2760 条请求不是 2760 次独立实验。本轮没有实现或比较复杂在线校准，不能由任何结果证明复杂算法无用，也不能自动批准 G0。

## 2. 固定策略及工程范围

两策略使用**同一个修改后 binary**，保存 binary SHA256、引擎基提交、实际补丁与工作树状态。对照 `original` 设置 `LLAMA_SERVER_SIMPLE_SCHEDULER=0`，走原始队列路径，保留原生 slot 亲和等选择行为，不能称为严格 FIFO；`simple` 设置为 `1`，仅改变待执行请求的选择次序，不称作未经修改的官方 binary。

请求显式传递 `request_class`（interactive/background）与 `client_req_id`。两 slot、非抢占、不预留空 slot：已有空位时，最老且已等待至少 **5000 ms** 的后台先选，其次最老交互，再次最老后台；同类按首次入队时间排序，同毫秒以内部任务 ID 打破平局。取消后不能再次选入。老化计时使用服务内部单调时钟。

5 秒是冻结的探索工程设置，不做本轮参数搜索，也不是后台等待/完成上界。它只保证决策时优先考虑已老化候选，不能承诺正在运行任务立即让位。记录实际选择、原因、等待与晋升次数；若主矩阵没发生晋升，不宣称已由主矩阵证明防饥饿。

原型不包含预测器、软余量、抢占、动态 prefill 或完整硬 KV 预留账本。容量仍由原引擎配置约束；真实取消恢复与日志闭合不能代替未来硬账本、幂等释放和长期公平性验收。

## 3. 采前冻结的最小矩阵

每轮保留原批次 `20261020-234210-p0-e0e1` 的 200 条交互（每 0.5 秒一条），从同批原 100 条后台按索引 `floor(k*100/30), k=0..29` 选 30 条。保留 req_id、原文、类别、temperature 和 max_tokens，交互上限 64、后台上限 384，不强制长度，不按输出结果删选或凑 token。源轨迹、所选 ID 与本次两轨迹采前复制并保存摘要。

| 条件 | 200 条交互 | 同一组 30 条后台 |
|---|---|---|
| steady 平稳 | 原到达点不变 | `250 + k*10000/3` ms，k=0..29 |
| burst 突发 | 原到达点不变 | 10 簇，每簇 3 条；`10000*g + 250 + 50*j` ms，g=0..9、j=0..2 |

| 重复 | 条件次序及每条件策略次序 |
|---|---|
| 1 | steady original→simple；burst simple→original |
| 2 | burst original→simple；steady simple→original |
| 3 | steady original→simple；burst simple→original |

共 12 轮，每轮 230 条，共 **2760 条测量请求**；每轮原两条固定预热，共 24 条另计。跨条件合计 original 先/后各 3 次。内容由历史冻结轨迹读取，本轮 seed=20261022 仅为批次标识，不重新生成提示。

## 4. 环境、测量和证据

引擎基提交 `620d2225cc436ab0b001e3200e590e3b286ef9ab`，模型 SHA256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`。启动参数保持 `-ngl 99 -c 4096 -np 2 -b 2048 -ub 512 --metrics`，每 slot 2048 上下文。核对原输入加输出上限可容纳；本轮实际输入、缓存和生成另记，不声称所有请求冷缓存或上限等于实际长度。

每轮先空闲观察 60 秒，记录 GPU 温度、利用率、显存、功率及相关进程；不结束无关应用。存在其他 GPU 计算任务或端口占用时暂停，不复用未知服务。每轮新服务，默认前缀缓存，固定两条预热，启动与预热限 120 秒。温度与宿主竞争记录用于解释，不能声称完全隔离。

100 秒开放到达测量窗口，最多 180 秒排空，单请求全过程总超时 180 秒；迟发门槛 50 ms。统一截止时关闭仍未完成连接并记录未完成；每条有唯一 ID、唯一终态、独立 JSON 和汇总。六终态：完成、拒绝、超时、取消、失败、未完成。

同一客户端 `time.monotonic()` 记录计划到达、释放、TCP 建连后且 HTTP 写入前的实际发送、首段非空生成文字、终态：
- **主指标：计划到达至首内容的交互 P95（total_first_ms）**，防止把等待移出计时。
- 同报发送至首内容 TTFT、迟发、全部终态和有首内容覆盖数。
- 服务内部接收/排队/选择时间仅用内部时钟差；不与客户端/GPU 墙钟直接相减。
- SSE 心跳、元数据、空内容不计首内容；SSE 字符块不冒称逐 token 时间。

采前运行受控客户端测试及真实引擎小序列策略验证（`tests/integration/verify_simple_policy_client.py`、`tests/integration/verify_simple_policy_engine.py`），覆盖关闭策略、优先选择、后台老化、取消清理和服务恢复。队列单元检查用过去时间验证 5000 ms 老化；真实正确性探针另用 1 ms 使老化分支快速触发、3600000 ms 隔离未老化交互优先分支，避免生成速度变化使测试条件反转。这些单独保存，不计性能样本、不用于调参；主矩阵始终使用 5000 ms。主采集前保存协议、配置、客户端、runner、测试、实际补丁、引擎/binary/模型指纹与轨迹快照。分析器 `scripts/analysis/86_analyze_simple_policy.py` 纳入采前源码清单；如果分析前再修正，保存实际版本并注明时点，事后分析修正使用新输出目录，不覆盖原始记录。

## 5. 分析和事先解释规则

每轮单独计算完成交互的 P50/P95，线性插值；每对报告 `P95(original)-P95(simple)` 的毫秒及相对改善，同时报告所有计划/终态、有首内容请求及其等待。存在非完成时，不仅凭完成者 P95 宣称整体改善。

逐轮报告后台从计划到达至终态耗时（逐条、中位数、P95、最大值）、实际 token 与缓存、finish_reason、在途曲线、100 秒窗口完成 req/s、排空及包含排空的全程输出 token/s。窗口内完成率与全程输出速率不能混用分母。没有可靠逐 token 时间时不计算精确窗口输出 token/s。

探索观察线为每对交互 P95 改善 **至少 100 ms 且至少 15%**；同时标记全程输出速率损失是否≤5%、后台 P95 完成时延增加是否≤20%，并列终态代价。这些只是尚未业务验证的观察线，**不是正式 SLO、显著性或 G0 自动通过线，不要求三对全部过线才报告结果，也不以过线直接宣布正式联合达标**。三对完整列出，可以列同条件同策略 r3 相对 r1 的变化供时间漂移检查，但不据此声称显著；不做逐请求独立 bootstrap，不把未检出差异写成等效。

结果分流：
1. 简单规则改善且代价可接受：可作为下一阶段基线，复杂机制仍须证明额外收益。
2. 改善但后台/吞吐代价较大：优先研究优先级、老化与配额取舍，另立开发协议。
3. 无改善且实际选择很少分歧：本场景没有形成充分决策机会，不能判断复杂度无用。
4. 有分歧仍无收益，主要受两 slot 正在运行任务限制：先评估简单后台并发/配额及非抢占边界，再决定预测校准是否有必要。
5. 任一结果仅限本设备、模型、内容与到达条件；不得为追求收益在本批后半程改变负载、老化或输出上限。

## 6. 暂停、保留与预算

容量异常、版本不符、终态不闭合、缺日志或发送迟发超 50 ms 等完整性错误，保留原轮并暂停后续采集；修复复验使用新 run_id，说明原因。**真实性能不利、超时、拒绝或未完成本身都不是删样或挑运行理由**，应保留并报告；如属于完整性故障，按前述规则处理。

最多 12 轮主测量，不因结果小或不利自动扩矩阵。预计 35—50 分钟机器窗口；按每轮测量+最大排空+空闲+启动预热计算，保守约 92 分钟。批次开始满 120 分钟不再开新轮；已有轮按单轮期限结束。至少 4 GiB 可用磁盘，新增证据预算 2 GiB，触及限额暂停。用户已说明时间够用，不以未核实人时阻止本次授权验证，也不把自动机时当人工投入。

完成后新增实验报告与带日期 G0 技术意见，区分已观察、解释和后续研究选择；不代导师签字，不覆盖 10-21 历史状态，不自动回填开题正文中的后续实验结果。
