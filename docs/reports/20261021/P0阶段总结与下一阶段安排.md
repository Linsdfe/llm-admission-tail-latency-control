## 一 目前做到哪里了

P0 主要是在确认三件事：模型能不能在自己的电脑上跑起来，测量工具靠不靠谱，以及加入后台长任务后，交互请求会不会明显变慢。

目前，P0 的八步技术准备和预实验已经做完。三组对照实验共完成了1500条测量请求，数据和运行记录已保存。但 G0 可行性复审还没有通过，所以现在不能把整个 P0 标成完成，P1 也还没有正式开始。

最直观的结果是：只有交互请求时，大部分请求很快就开始返回文字；加入后台任务后，较慢的一批交互请求要等到一百多秒才开始返回。这说明当前配置下，混合负载的等待问题值得继续研究。自己的 C++ 准入和调度策略还没有实现，因此这批数据还不是优化成果。

## 二 P0 具体做了什么

下面按工作内容归纳，方便理解，不替代原计划中的逐步验收记录。

1. 整理了研究计划、开发安排和项目目录，明确每个阶段要交付什么。

## 三 实验怎么跑的

E0 只有200条交互请求。E1 使用相同的200条交互请求，再加入100条后台请求。每组都分别跑 E0 和 E1，共重复三组。

交互请求每0.5秒到达一条，后台请求每1秒到达一条。两类请求的最大输出长度分别设为64和384个 token。token 可以简单理解为模型处理文字的小单位；这些数字是上限，不是每条请求实际生成的长度。

每轮重新启动服务，先做2条预热，再开始测量。六轮共12条预热不计入1500条测量样本。正式发请求的时间窗口是100秒，窗口结束后继续等尚未结束的请求，最多再等180秒。两种场景采用相同的计时口径。

## 四 数据说明了什么

这里关注的是“从客户端发出请求，到收到第一段非空生成文字”的时间，也叫 TTFT。收到 HTTP 响应头还不算开始生成，整篇回答生成完的时间也不是这个指标。

P95 可以这样理解：把等待时间从短到长排好，大约95%的请求不超过这个时间，仍有约5%的请求更慢。它不是最长等待时间。

| 重复轮次 | E0 交互 P95 毫秒 | E1 交互 P95 秒 | E1 额外排空 秒 |
|---|---:|---:|---:|
| 第1组 | 34.598 | 111.054 | 117.568 |
| 第2组 | 36.190 | 123.728 | 130.675 |
| 第3组 | 33.860 | 111.666 | 118.437 |

注意第二列和第三列的单位不同。E0 约为0.034到0.036秒；E1 约为111到124秒。E1 的交互 P50 也达到约58到64秒，说明变慢不只发生在极少数请求上。额外排空是100秒发请求窗口结束后，为处理剩余请求又等待的时间。

六轮共1500条测量请求全部完成，没有拒绝、超时、取消、失败或未完成。它说明本轮数据记录完整；不能由此得出“延迟已经达标”。E1 虽然最后都完成了，但用户等待很久。

## 五 后台任务也付出了等待代价

后台完成时间从计划到达时刻算起，一直到整条请求结束。它和前面的交互首字等待不是同一个指标。

| 重复轮次 | 后台完成数量 | 后台完成 P95 秒 | 后台最长完成时间 秒 |
|---|---:|---:|---:|
| 第1组 | 100 / 100 | 113.407 | 118.318 |
| 第2组 | 100 / 100 | 126.096 | 131.425 |
| 第3组 | 100 / 100 | 113.978 | 119.187 |

三轮 E1 的后台任务都完成了，但同样出现明显等待。以后评价调度策略时，需要同时看交互体验和后台完成代价，不能只把交互数据做漂亮，却不报告后台任务是否被拖得很久。

## 六 为什么目前可以使用这批测量记录

客户端会分别记录六类结果，而且每条请求只能有一个最终结果。测试覆盖了拒绝、断流、错误内容、总超时、主动取消和统一截止等情况。持续零碎地返回内容，也不能绕过请求总超时。

补充的30条完成与取消竞争测试，记录为10条完成、20条取消，数量能够对上，没有重复记账。真实模型服务在取消、超时和截止测试后，还成功处理了2条恢复请求，服务指标中的处理数和等待数回到了零。这只是客户端和服务恢复的检查，不代表后续自研资源账本已经验收。

正式采集前，先检查客户端能否按时发请求。第一次每秒500条的校准失败，最大发送滞后约293.888毫秒，这次失败记录已保留。之后把校准负载改为每秒20条，仍使用原先50毫秒的门槛，并在性能采集前通过检查。本轮正式实验的平均计划到达率最高为每秒3条。

六轮性能实验中，最大发送滞后为28.303毫秒，没有超过50毫秒门槛。这支持“本轮的大幅变慢不是客户端普遍晚发一百多秒造成的”这一判断；但还不能精确拆出服务内部每一段排队时间。

## 七 这批结果还不能证明什么

E1 同时增加了后台请求数量和生成工作量，所以不能只把延迟上升归因于“长短请求混在一起”。当前设置很可能受到过载影响：任务来得比系统处理得快，队伍越排越长。后续需要把总工作量增加和长度构成变化分开考虑。

从实际生成量看，每轮 E0 总共生成3985个 token；每轮 E1 的交互任务生成4010个，后台任务生成37838个，总计41848个。E1 的工作量明显更大。不能直接用这两个场景证明某种调度算法更好。

这里只重复了三组，使用的是合成请求。它们适合帮助判断方向、暴露问题，不能代替最终正式测试，也不能直接推广到其他显卡、模型或真实业务。

测试使用 RTX 3050 Ti Laptop 4GB 显卡、Qwen2.5 1.5B 的 Q4_K_M 量化模型，以及固定版本的 llama.cpp。服务有2个执行位置，每个位置的上下文容量为2048个 token。

目前尚未实现自己的 C++ 调度策略、硬资源预留账本、重复释放保护，以及服务端各段等待时间的记录。这些仍是后续开发任务。

## 十二 拿一条记录算给你看

以 r1-E1 的 I100 为例，原始文件是 r1-E1/replay/requests/I100.json。下面是字段节选，未列出提示词、回答全文和流式块序列；完整原文件保存在 data/raw/r1-E1-I100.json。所有 offset 都是相对本轮起点的毫秒数，不是北京时间。

```json
{
  "req_id": "I100",
  "arrival_offset_ms": 50000,
  "actual_send_offset_ms": 50001.33877300002,
  "first_content_offset_ms": 108253.38694600001,
  "end_offset_ms": 108457.10118700001,
  "send_lag_ms": 1.3387730000176816,
  "ttft_ms": 58252.048172999996,
  "max_tokens": 64,
  "terminal": "completed"
}
```

这条请求原计划在第50秒发出，实际约在第50.001秒发出，到第108.253秒才开始收到文字，第108.457秒完成。实际生成了19个 token，记录在 timings.predicted_n 中；64只是允许的最大输出量。

发送滞后 = 实际发出 − 计划到达。即50001.339 − 50000 ≈ 1.339毫秒，说明客户端基本按时发出了请求。

首字等待 = 首段内容到达 − 实际发出。即108253.387 − 50001.339 ≈ 58252.048毫秒，也就是58.252秒。

从计划到达到完成 = 完成时刻 − 计划到达。即108457.101 − 50000 ≈ 58457.101毫秒，也就是58.457秒。

首段内容到达后，到整条请求结束只用了约0.204秒。对这一条请求来说，主要耗时发生在首字返回之前；但其中包含哪些服务内部等待和计算，目前还没有完整分段记录，不能直接全称为纯排队时间。

计算应使用原始精度，最后再舍入。不要用本页三位小数的展示值重新计算，并要求末位完全一致。P95 也不是由这9条示例算出，而是分别对每轮200条交互请求计算；现有脚本采用排序后的线性插值。

## 十三 常用名词的通俗解释

交互请求和后台请求：交互请求通常是用户正在等答案的任务；后台请求通常可以晚一点完成。本次两类业务身份由轨迹预先指定，不是事后按输出长短重新分类。

LLM 和推理：LLM 是大语言模型；推理是已经训练好的模型接收输入并生成回答，本项目不做大模型训练。

token 和输出上限：token 是模型处理文字的小单位，不固定等于一个汉字。max_tokens 是最多允许生成多少，timings.predicted_n 才是服务端报告的实际生成量。

TTFT 和尾延迟：TTFT 是等到首段生成内容的时间；尾延迟关注较慢那批请求的等待。本次用交互 TTFT 的 P95 来观察尾延迟。

P50 和 P95：P50 约是中间位置的等待时间，P95 约是95%请求不超过的时间。它们都不是平均值；P95 也不是最大值。

流式响应和 SSE：模型边生成边发送内容，客户端逐块接收。SSE 是这类持续推送的一种格式；空块、心跳或响应头不当作首段生成文字。

开放到达回放和发送滞后：前者按预定时刻发请求，不等前一个完成；后者是实际发出比计划晚了多久。迟发严重会改变原本要测的负载。

预热和排空：预热先跑少量请求，让服务进入较稳定状态，不计入本次测量；排空是在停止发新请求后，继续处理已经提交的任务。

吞吐量：单位时间完成多少工作。请求吞吐用请求每秒，生成吞吐可用 token 每秒。本项目的窗口完成率只看100秒内完成数量，全程生成速率包含后续排空，不能混用分母。

slot 和上下文容量：slot 可以简单理解为引擎的一个执行位置；上下文容量是该位置能容纳的输入及生成历史范围。2个 slot 不等于所有请求都能立刻执行，也不等于有2块显卡。

prefill 和 decode：prefill 是处理输入内容的阶段，decode 是逐步生成后续内容的阶段。两者都会用资源，后续需要观察其相互影响。

KV 缓存和资源账本：KV 缓存保存推理中可复用的中间信息。资源账本是拟实现的记录与约束机制，用来管理可用量、预留和归还；目前还没实现。

SLO 和准入控制：SLO 是预先约定的服务目标；准入控制决定新请求现在进入、等待还是被拒绝。目标和规则要在正式对比前明确。

六类终态：completed 正常结束，rejected 被拒绝，timeout 超时，cancelled 主动取消，failed 运行失败，unfinished 统一截止时仍未完成。每条请求只记录一种。
