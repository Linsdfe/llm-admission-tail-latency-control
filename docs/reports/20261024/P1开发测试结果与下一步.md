## 1. 本轮实际做完的工作

新写了原生接口采集器、合成提示生成器、批次运行器和两份分析程序。在WSL启动真实模型，完成24条串行校准，再完成突发、平缓、稀疏三个场景各3次，合计9轮、2010条开发测量。20条模型预热另计。

只用现有引擎的原始顺序原型，含共同取消修复，不冒称未修改的B0或正式硬守卫B1。在线余量M、固定余量B3和正式硬账本尚未实现或比较。本轮不是最终算法验收，G1未通过，最终测试内容未生成或查看。

## 2. 数据先怎么看

聊天等待从计划到达算到首段实际回答。P95可理解为本轮约95%的聊天不超过这个时间。后台完成是整条任务做完。每轮发请求100秒，后台突发和平缓各30条，稀疏10条；聊天均为200条。

| 场景 | 三次聊天等待P95（秒） | 三次后台完成P95（秒） | 解释 |
|---|---|---|---|
| 后台成批到达 | 3.957 / 3.838 / 3.759 | 7.530 / 6.824 / 7.486 | 一批后台进来后，聊天会明显排队 |
| 后台均匀到达 | 1.090 / 0.779 / 0.827 | 4.713 / 4.319 / 4.280 | 比突发轻，但仍有尾部等待和轮间波动 |
| 后台稀疏到达 | 0.238 / 0.223 / 0.200 | 4.222 / 4.149 / 4.004 | 在这批条件下原始顺序已经较快 |

突发和平缓在同一重复中使用相同提示和输出上限，实际输出仍有差异，不能说计算量完全相等。稀疏还减少了后台工作量，不能把差别全部说成到达形状或长度的独立作用。三次只是开发观察，不作正式显著性或普遍阈值结论。

2010条开发请求全部正常完成，其他五类终态均为0，全部实际输入与冻结分词长度一致。最大发送迟发28.394毫秒，低于事先50毫秒线，没有挑选好看的运行。独立审计核对2054次真实启动和2054次释放（含校准、预热），最终占用与等待数归零。

100秒结束时，仅第一轮平缓剩1条请求，之后约0.0195秒完成；其他轮次为0。本次没有长时间窗口后积压，但100秒短跑不能证明长期稳定或持续负载可服务。

## 3. 输入和实际生成长度已经核实

提示采用显式Qwen ChatML，原生`/completion`执行；实际分词包含模板和特殊token，避免重复套模板。校准和开发模板家族分离，不是把P0请求换编号。

| 用途 | 聊天实际输入 / 输出范围（token） | 后台实际输入 / 输出范围（token） |
|---|---|---|
| 24条校准 | 50—155 / 11—64 | 128—653 / 100—384 |
| 2010条开发 | 53—155 / 11—64 | 128—658 / 81—384 |

开发聊天1800次执行中，630次达到64的输出上限；后台210次执行中，69次达到384上限。达到上限仍按真实原因记录，不能把上限直接当成实际长度或完整自然输出分布。同一内容在不同场景重放会重复计入这些执行次数。

## 4. 发现两项需要在冻结前处理的问题

第一项是余量可能没有变化空间。按24条校准暂取每类、每输入桶的输出中位数，有一组聊天预测为64，恰好等于64上限；有一组后台预测为384，恰好等于384上限。若总预测继续受用户上限裁剪，这两组加多少正余量也会裁回同一个值。约三分之一开发请求属于这些组。

每组只有4条校准，不能据此冻结预测器，也不能据此宣布M/B3整体冗余。其他组仍有余量空间；下一步要核对真实软决策能否因此改变，不能只看公式在变化。

第二项是最近邻适配草案的长短分类退化。草案曾建议用全部校准输出的85%分位作分界，本次该值为384；所有临时预测都不超过384，按草案会把全部开发请求判成短请求，长请求提拔机制无法介入。这是本项目草案的适配问题，不是原QBA方法无效的证据。

后续应在开发期完善校准规模、点估计与长短分界，保存原草案与修订依据，再冻结。不能看最终结果挑弱对手，也不为制造算法收益而改提示。完整计算见[预测余量诊断](../../experiments/20261024-025138-p1-development-validation-v1/diagnostics-v1/README.md)。
