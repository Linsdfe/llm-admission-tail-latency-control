# P1扩大校准与输出预算检查

2026-10-24，Asia/Shanghai。**本轮把问题查得更清楚了，但还不宜冻结G1：增加样本没有消除预测触顶，提高输出上限也不能直接解决回答质量问题。下一步先修订任务提示，再核对新负载。** 原课题仍比较“根据已完成请求调整保险余量”与“始终留固定余量”，不因本轮结果换题或预定复杂算法有用。

## 1. 这次具体做了什么

| 工作 | 实际完成 | 用来判断什么 |
|---|---|---|
| 扩大校准 | 120条新请求，5个种子；聊天/后台各3个输入档，每档20条，原来每档只有4条 | 原来预测触顶，是否只是小样本造成 |
| 新开发验证 | 另120条，聊天/后台各60条，每档20条 | 用没参与选型的新提示实例检查预测与分类 |
| 输出上限对照 | 从旧异常记录固定选8条，每条跑低、高两个上限，共16次 | 多给输出空间后，回答是否真的完成题目 |
| 完整性检查 | 主批12125项、探针441项程序核对通过 | 请求、原生token、启动/释放、来源与最终空闲是否闭合 |

主批240条全部完成，另2条预热，自动耗时491.787秒，约8.20分钟。最大迟发1.955毫秒，低于预先50毫秒门槛；242次启动与释放逐ID闭合。42份项目源、8份引擎源、23项运行清单和模型前后指纹一致。

输出上限对照16条全部完成，另2条预热，自动耗时102.068秒，约1.70分钟；18次启动与释放闭合。两批串行运行，服务退出码均为0。它们都是开发检查，不能当作并发调度性能对照；最终测试数据未生成或查看。

## 2. 多收数据后，预测问题解决了吗

没有。候选只有“同类别、同输入档的中位数”和“均值”。先轮流留出一个校准种子验证，另四个拟合，按主场景聊天200、后台30的比例计算误差，再选择候选。新开发验证不能反过来挑模型。

| 候选 | 校准留出验证的平均误差，按主场景加权 | 新开发验证的加权平均误差 |
|---|---:|---:|
| 中位数，按事先规则选中 | 17.833 token | 19.917 token |
| 均值，保留作参照 | 20.292 token | 19.890 token |

这里token是模型计算文本长度的单位。误差指“预测长度与实际执行长度相差多少”的绝对值平均。新验证两种加权误差很接近，但没有据此改选均值。均值能留出更多数值空间，不是本轮选型标准。

所选中位数用全部120条校准拟合后：

| 类别 | 实际输入token档 | 校准条数 | 输出长度预测 | 允许的最大输出 | 校准实际达到生成上限的条数 |
|---|---|---:|---:|---:|---:|
| 聊天 | 32—79 | 20 | 18 | 64 | 0 |
| 聊天 | 80—143 | 20 | 43.5 | 64 | 6 |
| 聊天 | 144—256 | 20 | 64 | 64 | 17 |
| 后台 | 128—319 | 20 | 214.5 | 384 | 5 |
| 后台 | 320—639 | 20 | 384 | 384 | 17 |
| 后台 | 640—1024 | 20 | 384 | 384 | 15 |

预测值可以是小数，实际生成token数仍是整数。三个档的预测已经等于最大输出，继续加保险余量仍会裁回原上限。

新开发120条中，**60条的点预测已到上限；加上校准留出误差的80%或95%分位余量后，两种总上界都达到100/120条触顶，即83.3%**。两种上界都另有4条实际输出超过上界。均值的点预测虽没有触顶，也不能因此认定加余量后的问题解决。

大白话说，很多请求已经按“最多能写多少”估计，再增加保险数也加不进去。扩样后这个现象依然明显。但这里比较的是静态长度数字，尚未测在线余量M和固定余量B3是否实际作出不同的放行决定，不能据此断言复杂算法一定没用。

## 3. 长短分类修订后怎么样

旧方案用平衡校准样本的85%长度分位，分界为384，所有预测都归短。新方案事先约定按主场景比例加权，算得分界64，新验证结果如下。

| 业务类别 | 预测短 | 预测长 |
|---|---:|---:|
| 聊天 | 60 | 0 |
| 后台 | 0 | 60 |

它不再“全是短请求”，但恰好等于聊天短、后台长。聊天在目标场景占86.96%，又最多输出64，得到这个结果有结构上的原因，不能拿零误分宣称预测特别强。

最近邻规则的配额欠账、等待历史和提拔操作仍可能与简单业务优先不同，需要后续真实实现核对。不能仅因分类相同就把整套方法判成等价，也不能继续换阈值制造容易击败的对照。候选修订见[适配补充v2](../../p1/nearest-neighbor-adaptation-amendment-v2.md)，尚未冻结。

## 4. 多给输出空间，回答就好了吗

本次选8条已发现问题的旧提示，聊天比较64/128、后台比较384/768，保持提示和模型不变。它们是后验选例，不能估计全部请求的回答合格率。下表是执行记录及助手逐条阅读后的探索判断，不是学生、导师或人工盲评结果。

| 选例 | 低/高上限下实际输出token | 观察及含义 |
|---|---:|---|
| 聊天c05、c11 | 各64 → 99 | 高上限自然结束，但主要完整抄录补充记录，不能当作两句话解决原问题 |
| 聊天c17 | 64 → 128 | 高上限记录的停止原因是EOS，仍编造分钟与页数换算；EOS不等于正确 |
| 聊天c23 | 49 → 49 | 两档自然结束、用词有差异，仍把时间管理建议混进文具预算问题 |
| 后台c04 | 384 → 581 | 高上限自然结束，仍主要在三类标题下抄录记录，没有完成要求的六点分析 |
| 后台c08 | 384 → 768 | 两档均到生成上限，继续罗列数字 |
| 后台c18 | 384 → 52 | 高上限反而变短，却无依据断言1—22正常、23异常，未完成六点要求 |
| 后台c22 | 384 → 768 | 两档均到生成上限，仍停留在第1点反复列数，8字符重复超额比率0.840 → 0.920 |

8条低上限中1条自然结束，高上限中6条自然结束；这8对实际输出合计1777 → 2544 token。自然结束变多、输出变长，均不等于回答完成任务。重复指标只描述文本，不自动判分；完整全文、判断依据和限制见[逐对核读](../../experiments/20261024-1926-p1-output-budget-probe-v1/README.md)与[客观表](../../experiments/20261024-1926-p1-output-budget-probe-v1/metrics.md)。

同提示两档输出有非前缀差异，顺序和缓存未完全控制，不能把某次变好或变坏全部归因于上限。当前证据支持先处理提示遵循和任务定义，不能直接把主预算翻倍作为修复。

## 5. G1还差什么，下一步怎样做

| 事项 | 本轮已经有的证据 | 接下来具体做法 |
|---|---|---|
| 任务和输出预算 | 有长度数据，也有复述、重复、未按要求作答的选例 | 另登记提示v2，明确原题、记录用途和最终回答格式；按任务完成情况核读，再核实际输入/输出与负载。v1数据始终保留 |
| 公共预测器 | 120校准、120新开发；预定规则选中位数，触顶未消失 | 当前工件只作开发候选。若提示或预算改变，重新核对校准与开发，不沿用旧长度当作新任务事实 |
| 强对照 | 加权64分界与业务类别重合已明确 | 保留最近邻候选，核对实际排序和提拔；真正等价时登记配置别名，避免伪造不同方法 |
| 复杂算法的介入机会 | 本轮只有静态上界，没有实际M/B3决定 | G2/G3实现最小可观测路径，记录硬允许时两者何时放行/等待不同，再决定完整实现范围 |
| 正式比较规模和判据 | 仍是开发方案，旧9轮不能替代新策略波动 | 冻结目标与代价、开发选参、独立重复规模和顺序；最终测试继续隔离 |

下一项先做提示与任务版本修订，并检查它是否仍代表要研究的长短混合服务。改动依据是任务能否完成，不按哪个设置让复杂算法获胜来挑样本。若改了主任务或预算，必须另测开发负载；本轮不会自动通过G1，也没有实现正式硬账本或M/B3性能比较。
