# G0评审材料：实验、解释与待决定事项

实验截止：2026-10-23；材料于2026-10-24完成收尾核对（Asia/Shanghai），按实验日期归档。供用户逐项评审，最终决定留空；不代填导师或学院批准。本报告是新增阶段记录，早期报告、失败运行和冻结方案均保留。

## 一、先说现在到哪了

**G0所需的技术实验已具备评审条件：机器能跑、测量能核对、问题在部分场景确实存在、C++改动能生效，容量超界后的恢复也补测了。现在主要需要你评审研究范围、服务要求、论文贡献和投入是否合适。**

已有四批完整性能实验，合计42轮、9630条测量，84条预热另计。本次复核这些证据，新增9次容量边界正确性请求，其中2次预热；没有把旧实验当新跑，也没有把正确性请求混入性能样本。

这次G0决定的是“基础是否够、是否值得继续做”。在线校准是否胜过简单方法还没验证，不能在G0先写成结论。

## 三、实验做了什么，数据说明什么

先统一读法：**聊天等待**是请求到首段实际回答内容的等待，不是整篇回答生成完。P95可以近似读成“本轮约95%的聊天不超过这个时间”；它不是平均值，也不是最慢一条。表中的范围是三次独立运行结果的最小到最大，不是置信区间。后台完成时间是整条任务做完；全程输出速率把最后等积压做完的时间也算进去。

前两批聊天等待从“实际发出请求”开始，后两批从“计划到达”开始，后者还包含客户端迟发。只在同批、同口径下比较；下面不把四批性能拼成一个总体。

### 实验1：设备能跑，输入太长时会怎样

设备固定为4GiB显存的RTX 3050 Ti Laptop，模型为Qwen2.5-1.5B Instruct Q4_K_M。服务有2个执行位置，每个上下文2048 token。token是模型处理文本的长度单位，不等于汉字个数。

原有多次构建/加载与性能运行已完成。本次再新启一个服务，补最小容量探针：

| 发什么 | 实际返回 | 说明 |
|---|---|---|
| 2条短预热 | 均成功、各生成8 token、未截断 | 服务正常启动 |
| 输入2047、要求最多生成1 | 成功，实际评估2047并生成1；同时报告碰到容量限制停止 | 输入被处理了，但已经挤到边缘，不能当作“完整预算无截断通过” |
| 输入2048和2049，各一次 | 均明确返回HTTP400与“超出上下文容量” | 输入本身占满或超过容量时，不能再正常留生成空间 |
| 每次错误后各一条后台、一条聊天 | 4条全部成功，各生成8、未截断 | 同一服务能接着工作 |

9次请求都有真实的9次启动和9次释放，结束活动位置和后台计数均为0，两个位置空闲，进程正常退出，代码/运行库/模型前后一致。两次错误也曾占用执行位置，随后释放；没有把HTTP报错当作“从未占用”。4条恢复实际复用同一个位置，不能扩大为所有位置都已重新复用。

**判断：G0要求的容量可观察、超界明确报错和本次错误后恢复已经有证据。完整输入加输出的硬预留账本、所有取消路径正确性，仍属于后续工程验收。** [补测详情与时间勘误](../../../results/raw/development/20261023-2256-g0-context-boundary-v1/README.md)，[机器可读结果](../../../results/raw/development/20261023-2256-g0-context-boundary-v1/summary.json)。

### 实验2：会不会是测量工具自己把结果拖慢了

对测量工具单独检查，避免直接拿性能数字讲故事：

| 检查 | 数据 | 说明 |
|---|---|---|
| 每秒发20条，合计200条校准 | 最大迟发2.00毫秒，低于事先50毫秒线 | 当前发送器能按要求发出小请求 |
| 完成与取消接近同时发生 | 30条中10完成、20取消，无重复终态 | 不把一条请求重复算两次 |
| 一直有小段输出但超过总时限 | 仍能触发总超时 | 不能靠滴流永远拖住客户端 |
| 人为让每次落盘多花80毫秒，40条 | 旧同步记录最大迟发821毫秒；新异步记录2.88毫秒，两组40条都完成 | 旧工具确实可能干扰发送，修复有效 |
| 四批完整性能实验 | 9630条全部完成；各批最大迟发18.3—33.1毫秒，均未越50毫秒 | 终态和迟发门槛闭合，不只挑成功样本计算 |

客户端保留完成、拒绝、超时、取消、失败、未完成六类结果；服务端实际释放另查，客户端超时不等于服务器立刻释放。[工具检查原始结果](../../../results/raw/client-verification/20261023-1440-background-cap-client-v2/summary.json)。

**判断：当前测量链可用于继续实验。旧失败和负面结果没有删除，也不能把旧真实性能恶化全部归咎于写盘。**

### 实验3：后台一多，聊天真的会受影响吗

第一批6轮、1500条测量。每轮都是100秒内200条聊天；对照不加后台，另一条件加100条后台，每种条件各跑3次。

| 条件 | 三轮聊天P95 | 100秒发送结束后，还要等积压做完 |
|---|---|---|
| 仅聊天 | 34.6 / 36.2 / 33.9毫秒 | 0秒 |
| 相同聊天，再加较密后台 | 111.1 / 123.7 / 111.7秒 | 117.6 / 130.7 / 118.4秒 |

**说明：这批负载下确有严重拥堵，连首段回答都可能等近两分钟。** 但加后台后实际总输出由每轮3985增加到41848 token，约10.5倍；这不能单独证明“因为长短不一”或“因为后台这个标签”造成恶化。它包含新增工作量与过载的作用。[完整第一批](../../experiments/20261020-234210-p0-e0e1/README.md)。

### 实验4：后台很少，还需要复杂方法吗

第二批6轮、1230条测量。保持200条聊天，后台降到每10秒1条、每轮10条；各条件3次。

| 条件 | 三轮聊天P95 |
|---|---|
| 仅聊天 | 25.8 / 40.3 / 34.0毫秒 |
| 加稀疏后台 | 48.9 / 58.2 / 48.5毫秒 |
| 同轮增加了多少 | 23.2 / 17.9 / 14.5毫秒 |

三轮都没有窗口后的积压；各轮9个后续后台到达前检查均已清空。**如果服务允许等1秒，这里的原方法已经很快；当前没有展示出必须加复杂方法的需求。** 1秒只是待评审的工程假设；这也不等于证明所有低负载都没干扰或复杂算法永远不值得。[完整稀疏实验](../../experiments/20261021-093300-p0-lowload-v1/README.md)。

### 实验5：先用最简单的规则，能解决多少

简单规则已经实际写入C++：**有空位时先让排队的聊天进；后台排队满5秒会被提到前面；已经开始生成的任务不中断。** “后台满5秒提升”提供服务机会，不保证5秒内完成。

上午完成12轮、2760条测量：每轮相同200条聊天加30条后台，分别均匀到达或每10秒集中3条；原路径和简单优先各重复3次。

| 条件 | 原路径聊天P95 | 简单优先聊天P95 | 解释 |
|---|---:|---:|---|
| 后台平缓到达 | 348—457毫秒 | 321—408毫秒 | 本来就不慢；三对实际启动顺序完全一样，不能把波动说成规则收益 |
| 后台成批到达 | 3.12—3.25秒 | 2.87—3.02秒 | P95改善约5%—12%，但仍有一部分聊天等几秒 |

突发时聊天中间位置的等待P50从690—894毫秒降到61—66毫秒，说明多数聊天受益；但后台完成P95增加8.7%—13.6%，全程输出速率损失0.18%—0.55%。**规则有作用，但“多数人快了”和“最慢的一批也够快”是两件事。** [上午12轮](../../experiments/20261023-100000-p0-simple-policy-v2/README.md)。

### 实验6：后台最多同时一条，会不会两头都好

下午另跑18轮、4140条测量：在同一个最终新引擎中比较原路径、简单优先、简单优先加“后台最多同时一条”；仍是200聊天加30后台、两种到达方式、每种3次。三种方法的执行顺序做了平衡。新引擎包含共同取消修复，所以只做本批同期比较，不把上午和下午硬配对。

| 到达方式 | 原路径聊天P95 | 简单优先聊天P95 | 再加后台上限后的聊天P95 |
|---|---:|---:|---:|
| 平缓 | 242—351毫秒 | 208—347毫秒 | 49—58毫秒 |
| 集中突发 | 2.99—3.06秒 | 2.79—2.83秒 | 53—61毫秒 |

聊天确实快很多，代价如下，均为“简单优先→再加上限”的同期对照：

| 到达方式 | 后台完成P95 | 全程输出速率损失 |
|---|---|---:|
| 平缓 | 3.76—3.95秒 → 10.71—13.32秒 | 6.90%—8.98% |
| 集中突发 | 7.98—8.07秒 → 16.41—19.10秒 | 6.89%—9.10% |

每轮的配对代价见完整数据；上面范围不用于跨轮相减。加上限的6轮，在100秒结束时还各有3—4条任务没做完，之后再花7.15—10.25秒排空；不能据短跑认定长期不积压。

**说明：给聊天留位置有效，但不是免费提速。** 按采前的探索线“聊天P95≤1秒、后台P95增加≤20%、速率损失≤5%”，6对都达到聊天线，6对都超过代价线。因此没有支持全局固定开启此上限；如果你愿意接受后台更慢，这又可能是可以接受的取舍。这些线需要你评审，不能冒充真实业务要求。

服务日志的4176次启动和4176次释放（含36预热）全部闭合；上限组后台同时运行数确实最多1。聊天排队P95由简单优先突发时约2.75—2.78秒降到约12—13毫秒，后台排队则明显增加，说明主要是把服务机会重新分配了。[下午18轮逐轮数据和核对](../../experiments/20261023-151822-p0-background-cap-v1/README.md)。

## 四、有没有藏掉不好看的实验

没有。42轮指四个完整批次，不包含另外两批失败v1；两批失败单独保留：

- 第一批：原路径首轮230条完整；第二轮仅留下33条终态，其余197条结局未知，后10轮没开始。进程消失原因未确认，不能补写为“197条超时”。
- 第二批：原/简单各230条都完成，但简单轮有2条迟发超过50毫秒，按规则停止后10轮。聊天P95反而从0.516秒恶化到6.961秒。慢磁盘检查证明工具可能干扰，却不能解释全部6.45秒差距；队列和批处理等因素未被排除。
- 改异步记录后，新版12轮全部重跑；后续18轮也完整保留。没有挑一轮好看的替换坏结果。

另外，C++规则检查28个断言、真实引擎8组探针通过；其前两版探针因错误的计时/入队假设失败，也保留了。仍有一条已登记的原路径/简单模式窄取消唤醒边界，不能说所有生命周期验收都做完了。

完整批次每个条件只有3次独立重复、每轮100秒，9630条共享队列请求不等于9630次独立实验；本报告不宣布普遍最优、正式显著性或长期稳定。完整逐轮值、指纹检查、失败来源和检查索引见[独立汇总](../../../results/raw/maintenance/20261023-g0-consolidation-existing-audit-v1/README.md)及[summary.json](../../../results/raw/maintenance/20261023-g0-consolidation-existing-audit-v1/summary.json)。

## 五、原课题继续研究什么，别人做过什么

原课题主问题保留：**两套方法用相同的估计器、排队顺序、后台保护和容量约束，一套留固定保险余量B3，一套根据已完成任务的误差在线改余量M；后者到底多带来多少收益、付出多少代价？**

现有实验为后续提出了依据：不限制后台，突发聊天可能等很久；一刀切限制后台，后台又明显变慢。在线调整是否能改善这项取舍，还是与固定余量相比没必要，仍需后续验证，不能由现有上限结果推出。

文献核对发现：ConServe、HyGen已研究在线/后台混合服务；TIE、QBA、UniBoost研究排序、风险或长请求保护；**MAPS已经有最近完成样本、正误差分位数、滑窗在线更新余量，与M核心形式直接重合。** 因而不能把“在线校准本身”或“用更小显卡”写成算法创新。[六篇原文方法、出处与适配边界](G0最近邻核对与原课题边界.md)。

可以继续做的是这套具体受限系统的实现与公平对照，并检验在线更新的实际增量。它能否满足学校对本科毕设贡献的要求，要由导师认可；当前没有证据保证算法创新。若后面没收益，也应据实报告，不能为了原题预设M一定赢。

| 阶段 | 要回答的问题 |
|---|---|
| 现在G0 | 基础能否支撑继续，问题/范围/贡献和投入是否接受 |
| P1/G1 | 明确唯一主场景、什么算有用、怎么公平比较，冻结方案与数据划分 |
| P2—P3 / G2—G3 | 在硬容量允许时，M/B3究竟会不会作出不同决定，有没有可解释介入机会 |
| P4/G4 | 实现核心方法，核对更新与控制是否按设计工作 |
| P5/G5 | 用完整同期对照和消融，最终判断额外收益是否抵得过后台、速率、决策和维护成本 |

## 六、后面时间够不够：已知与未知分开

上午12轮机器耗时34.22分钟，下午18轮52.87分钟，折合现有设置下每轮约2.85—2.94分钟，包含该批次编排开销。按同样长度粗略外推，50轮约2.4小时、100轮约4.8—4.9小时，**只是自动运行的参考，不是完整研究所需时间。** 新场景的长度、积压与故障会改变耗时，不能拿此承诺未来成本。

还要另计实现、调试、核对、校准/开发与正式测试划分、必要复验、至少一次2小时稳定性运行和论文写作。原计划250人时是初估，已用与剩余有效人时没有可靠记录；由本人补可投入时间与设备时段，P1据正式矩阵重算。现在无需为“凑齐G0”先跑两小时稳定性或所有正式矩阵。
