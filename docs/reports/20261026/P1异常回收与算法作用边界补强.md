# P1异常回收与算法作用边界补强

本轮继续提高了工作质量，按同一套五项量表，**84分提高到88分**。实质改善是异常处理已在真实模型上走通，并能用完整数据解释“在线余量为什么没有改变放行”。尚未证明复杂方法有额外收益，仍不建议按90分线直接通过G1。

## 1. 修了两个可以复现的具体问题

旧版遇到503拒绝后，还等这个请求的原生释放；但请求根本没有进入模型，不会产生释放，最后把拒绝改记成failed。旧版遇到永久放不下的请求，也不立即拒绝，会一直等到timeout。这两种错误已用保留的旧代码实际复现。

新版分别处理：排队中取消就移出队列，超容量立即拒绝；已获得额度但没有写出请求，可以直接归还；已在模型运行的请求必须等原生CAP释放。明确HTTP拒绝且没有原生启动时，只有独占实例确认全部slot空闲，才按拒绝证据回收。请求本来的终态和控制层错误分开保存，资源和反馈均只处理一次。

若已经发送，却既无释放又无可信拒绝证据，3秒后隔离额度、停止新放行，让批次验收失败。故障注入确实验证了“缺释放不能假装回收成功”。这项缺失释放测试是合成注入，不是原生GPU故障实验。

## 2. 真实模型具体测了什么

WSL本地3B、原固定引擎、2个slot、每slot2048的配置保持不变。一次独占服务连续运行8个场景；每个场景结束后，再发1条正常请求检验同服务恢复。共18条计划正确性请求，实际发送15条，其中14条进入模型；另有2条预热。它们是开发正确性夹具，复用已见提示，不是新独立资料或算法性能对照。

|场景|主请求结果|资源和记录核对|随后同服务恢复|
|---|---|---|---|
|正常请求|completed|释放后归还、反馈一次|完成|
|排队时取消|占位任务完成，排队请求cancelled|取消请求没有发送|完成|
|排队时超时|占位任务完成，排队请求timeout|超时请求没有发送|完成|
|运行时取消|cancelled|确认本请求原生释放，不反馈|完成|
|运行时超时|timeout|确认本请求原生释放，不反馈|完成|
|永久超容量|rejected|没有发送，没有占用额度|完成|
|非法grammar触发HTTP400|failed|明确HTTP错误＋独占空闲后回收，不编造释放|完成|
|达到统一截止|unfinished|关闭连接后确认原生释放，不反馈|完成|

18条终态合计为：11完成、2取消、2超时、1拒绝、1失败、1未完成。这里的失败、超时和取消是事先设定的测试目标，不能混入算法性能统计。原生记录包含16次启动和16次释放，其中2对是预热；服务正常退出。338项独立核对通过，8次恢复全部完成。

合成测试另测15个场景，包括连接失败、SSE截断、未知输出长度、重复回调、临时日志读取错误和缺释放隔离。首次Windows夹具把Linux错误号61写死，导致临时读取负例不符合Windows的错误号；失败目录和当时源码保留，改用平台errno.ENODATA后，WSL完整门禁通过。没有因此修改真实模型成绩。

这仍是Python客户端准入原型。HTTP拒绝的空闲回收依赖独占实例，不能原样推广到存在其他客户端的服务；尚不等于正式C++控制器或完整KV生命周期验收。

## 3. 为什么在线算法仍没有收益

本轮没有换一个有利预算重跑。读取前一轮全部4064个真实状态，计算每个状态下两种方法究竟在哪段预算内会作出不同决定。这里只固定当时的队列状态，不能当成改预算后整个队列的运行结果。

|已有数据中的情况|完整计数|说明|
|---|---:|---|
|第一版保守下限|2193个状态|在线余量和零余量连成本都相同|
|第二版估计成本不同|164个状态|在线余量确实改变了估计|
|其中空系统启动|30个状态|公共规则直接允许启动，余量不起作用|
|其余可由预算影响的状态|134个状态|已全部计算能让决定分叉的区间，没有挑选|
|当前预算落进这些区间|0个状态|解释了为什么没有改变放行|

这134个状态中，在线余量只多了1或2个token，对应的分叉区间宽度约为当前预算的0.87%—1.74%。当前预算离最近的区间边界仍有约3.84%的距离。因此在这些已观察状态下，估计虽变了，决定仍相同。完整边界的下沿、内部和上沿均已核验，另有4905项独立复核通过。

白话说，**这次不是“算法没有执行”，而是“算法调得很小，没有跨过改变放行的那条线”**。这支持收窄当前负载的结论，不能推出一般LLM服务都不需要在线校准，也不能从区间推导出调预算后的延迟收益。

## 4. 多算余量到底贵不贵

单独取出同一组实际状态，只测Python长度/余量计算，9个顺序平衡的计时块，每方法每块59872次调用。高分辨率墙钟的每次调用中位数：零余量约0.52微秒、固定加1约0.50微秒、在线余量约1.51微秒。

在线方法多出的约1微秒很小，不能拿它解释之前49—68毫秒的交互尾延迟波动。本次只测计算组件，没有包含维护历史、排队、日志、HTTP或模型执行，也不能外推C++生产开销。现有证据更准确的说法是“当前条件没有观察到额外收益”，还不能说“复杂方法计算太贵，所以不值得”。
