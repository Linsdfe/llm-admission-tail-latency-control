# P1质量补强与同口径复评分

截至2026-10-26，本轮把工作质量从**76分提高到84分**。评分仍用原来五项各20分的量表。补上了采前检查、样本不足和真实反馈验证；还没有证明复杂方法值得使用。90分通过线下，我仍不建议现在直接通过G1。

## 1. 原来缺什么，这次补了什么

|原来的具体问题|这次实际做的事|核对结果|
|---|---|---|
|旧验证漏查邻接批次，混入2份重复提示；有提示实际80 token却要求不超过79|把全历史查重、真实分词、上下文和允许的数据划分放进统一采前入口；拿旧错误回放|重复、超桶、样本不足均被同一入口拒绝；216份新来源资料通过，生成未按答案筛选|
|后台每类最多28条，达不到32条的在线更新门槛|新增144条真实校准，与旧48条合用|六类各32条，不降低门槛，不复制旧答案凑数|
|之前只有离线算术，不能说明真实模型反馈下会怎样|实现共享Python准入原型，连接WSL本地3B模型，比较固定余量0、固定余量1、在线余量|13轮有效负载，每轮230条全部完成；每轮真实反馈为交互68/68/64条、后台12/10/8条|
|请求结束和槽位释放可能不是一回事|观察原生CAP释放后，才归还外部额度并加入误差历史|有效轮次的额度、释放、反馈先后均通过独立核对；不读取未来输出|
|公开最大长度可能把在线余量盖住|先保留最大长度作软估计下限，再另登记一次“只作上限”的6轮开发对照|第一版成本也无差异；第二版成本出现差异，放行仍未出现差异，见下表|

固定余量0就是直接使用长度预测；固定余量1是在预测上始终加1个token。在线余量M按已经完成请求的误差更新，窗口32条、取80%分位。本轮观察到了0、1、2个token的在线余量。三种方法用相同信息和候选顺序。

硬容量始终按“实际输入＋用户最大输出＋1”预留，最多2条在途、总额不超过4096；每条不超过2048。软估计只决定何时放行，不减少硬预留。当前是客户端共享原型，尚不是正式C++控制器或完整KV生命周期实现。

## 2. 新数据怎么算

|有效数据|测量次数|预热次数|用途|
|---|---:|---:|---|
|新单条校准|144|2|补齐暖启动，确定公共成本|
|第一版：1轮预算探针＋6轮对照|1610|14|公开最大长度作为软估计下限|
|第二版：6轮对照|1380|12|公开最大长度只限制软估计上限|
|合计|**3134**|**28**|校准复用不重复计数|

这些是请求出现次数，不是3134份独立资料。新来源共216份，其中开发比较每版只有2组。两版复用相同资料，分时段运行，不能当作4组独立重复，也不能把跨版性能变化完全归因于软估计角色。最终测试资料未生成或访问。

系统完成和答对分开：新校准107/144完整正确；两组比较分别182/230、186/230完整正确，三方法一致，约79.1%和80.9%。这些是受限格式合成任务，不能冒充真实业务质量验收。答案由程序逐字段核对，助手复核汇总和代表记录，没有人工逐条通读3134份答案。

## 3. 复杂方法到底有没有作用

表中“同状态判断”是把同一时刻的真实队列交给三种规则计算，不是另外生成请求，也不是另一策略完整运行后的反事实性能。

|观察项|第一版：最大长度作下限|第二版：最大长度作上限|
|---|---:|---:|
|同状态判断次数|2193|1871|
|在线方法与零余量估计成本不同|0|164|
|在线方法与零余量放行决定不同|**0**|**0**|
|在线方法与固定加1放行决定不同|18|7|

第一版的保守下限吸收了在线变化。第二版已出现估计成本差异，但变化仍不足以跨过当前预算边界，所以没有改变放行决定。固定加1也有少量差异，不能把它的表现当作复杂方法优于最强简单对照的证据。

下面用第二版两组主对照看实际表现。交互P95表示从计划到达到收到首个内容，95%的交互不超过这个时间；后台P95从计划到达到任务完成。全程速度按至少100秒并包含排空的窗口计算。

|组别|方法|交互P95，毫秒|后台P95，毫秒|输出token/秒|
|---|---|---:|---:|---:|
|32101|零固定余量|513.5|2894.3|34.39|
|32101|在线余量|562.8|2850.6|34.39|
|32102|零固定余量|839.8|3461.8|38.94|
|32102|在线余量|908.0|3501.2|38.94|

在线方法的交互P95分别慢49.3和68.2毫秒，没有观察到收益。后台变化分别为快1.51%、慢1.14%。只有两组开发数据，加上同状态放行一致，不能把这点波动解释成稳定优劣或统计等效。第一版也未呈现稳定收益，全部轮次见实验入口。

记录中的决策P95约29.6—40.1微秒，包含同时计算三个影子策略和共享观测的成本，不能据此给在线方法单独报价，更不能直接宣称其生产开销划算。

## 4. 中途失败也算账

第一次试跑遇到WSL共享文件读取错误，230条计划中仅1条实际发出，客户端最终230条失败。第二次修复后仍漏读一次释放，实际发出35条，34完成、196失败。两个轮次不能作为有效性能对照，原始记录和当时源码全部保留。

随后修为有界二进制读取、显式保存读取偏移；临时无数据时不推进偏移。增加故障注入和共享文件1000组启动/释放回归，复跑不重采144条有效校准。最终两版有效轮次共2990条负载请求全部完成。

还有一次明确的方案补充：原来要求后台至少一半必须按普通预算启动，忽略了合法的空系统启动。首次探针结果出来前，已另存补充口径，分别查正常完成、普通＋空系统启动比例、自身成本能否放进预算。探针普通12条、空系统18条、老化0条，自身成本能放进预算24/30。**原普通启动15/30标准未通过；补充标准通过**。旧标准和登记时间保留，不把它写成按原标准成功。

## 5. 为什么是84分，还缺什么

这仍是助手按工作质量作的主观评分，不是统计量，也不是论文完成度。旧“材料准备程度90分”不再代替这个固定量表。

|维度，每项20分|原分|现在|加分依据与剩余缺口|
|---|---:|---:|---|
|研究问题与贡献|13|15|有真实机制证据支持收窄结论；尚不能回答一般LLM负载何时值得复杂化|
|负载与机制匹配|12|15|暖启动和真实更新已落实，查清成本差异未越过预算边界；当前任务仍缺少足够辨别力|
|实验设计与对照|15|17|公共预算不看M结果选择，同信息强对照、有限停止、全终态齐备；仅2组开发，补充口径与角色探索需正式重锁|
|数据可信与复核|18|19|统一采前门禁、旧错回归、失败和复用计数可追踪；单机、开发资料复用限制仍在|
|阶段工程交付|18|18|真实释放后反馈可用；两次读取故障说明集成可靠性还需加强，完整异常合同尚未验收|
|合计|76|**84**|不因多写文件、多做检查或M输赢加分|

要继续提高，应先补这几项实质内容：

1. **把研究范围定准。** 若保留当前固定格式任务，就研究简单方法的适用边界；若要讨论一般LLM调度，另登记仍可核对、自然输出工作量有变化的场景，不能按M输赢筛选。
2. **重新锁定正式方案。** 正式六桶暖启动建议192条；明确最大长度在软估计中的角色，保留保守公共语法策略作强对照，重新列矩阵。现在的开发144条不冒充正式新校准。
3. **验证完整运行合同和方法成本。** G2/G3完成C++状态、取消、超时、释放回收与恢复核对；单独测各策略开销，再用独立重复和未见资料验证收益及后台代价。本轮不提前执行最终测试。

G1仍由用户评审，当前建议继续补强，不因这次84分自动通过。
