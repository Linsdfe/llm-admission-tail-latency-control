# G1补强：现在是否值得进入下一阶段

**我的建议是G1可以通过，按方案准备程度评90/100；最终决定留给用户。** 本次补齐M/B3作用空间核对与无增益时交付路线，另修订了公共预算参考。评分是主观方案评审，不是算法效果或统计质量分数，G1未自动通过。

## 先把机制核对的结果说清楚

|问题|核对结果|意味着什么|
|---|---|---|
|M和固定余量B3是不是完全一样|候选逻辑可构造出相同状态下一放一等的例子|规则有区别，但尚未证明真实队列会到这个状态|
|现有资料需要M修补多少低估|48份已见开发输出都未超过“B3余量0＋共同语法上界”；非核对任务没有正残差|当前负载的在线校正空间很小，不能承诺M会赢|
|差别主要在哪|4种M配置的1840次离线诊断里，相对B3=0有544次多留1token，其余1296次预算相同；多留来自冷启动回退|这是保守程度的差别，不是544次真实放行差异，更不是性能收益|

离线诊断复用48份资料与单条输出，按两个种子各230次出现构造外生反馈；没有模拟真实2slot、批处理或策略改变完成时间。本次没有新增GPU测量，最终测试未访问。[完整诊断及独立核对](../../experiments/20261026-p1-margin-mechanism-audit-v1/summary.json)、[独立核对结果](../../experiments/20261026-p1-margin-mechanism-audit-v1/independent-audit.json)。

所以后续不是直接跑大矩阵“证明M好”，而是先在G2/G3把真实状态、反馈与放行日志做好，核查规则确实执行。如果实现正确但本负载没有触发，就按负面结果路线交付，不改数据追胜利。

## 发现并修订了一个预算问题

旧参考成本按200/30比例取75%分位，容易被数量较多的交互请求主导。旧三个候选下，24/24份后台来源任务自身成本都超过预算，普通非空状态很难满足软准入，只能等待空系统或老化绕过。这是成本代理分析，不是实测饥饿。

候选v3改成分别计算交互、后台的校准P75，再取较大值。三个倍率和搜索规模不增加，所有方法共用。现有点成本示例中，最大候选下不再单独超过预算的后台资料为14/24；仍有10/24超过。正式校准将按完整公共语法规则重算，不能照抄示例值。[预算诊断](../../experiments/20261026-p1-budget-reference-audit-v1/summary.json)。

## 没有M增益，论文仍须交付什么

|必须交付|具体内容|
|---|---|
|可用系统|C++接入、队列、硬容量、软准入、后台保护、取消/超时与回收|
|正确性证据|六终态闭合、超容量拒绝、一次释放、异常恢复和稳定性|
|公平实验|M/B3同信息、强简单对照、全部结果与不确定性、方法成本|
|有边界的结论|区分“满足要求”“收益达不到预设幅度”“代价超线”“证据不足”，不把没显著改善写成普遍无用|
|可复核材料|代码、配置、数据来源、原始失败、分析、哈希、归档与复现命令|

具体验收和论文各章写法见[无增益交付计划](../../p1/negative-result-delivery-plan-v1.md)。系统错误不能靠性能结果抵消；没有触发不能自动证明所有状态下等价；原矩阵仍按登记规则执行，除非用户另行评审修改范围。导师/学院是否接受系统实现型毕设，仍需其正式意见。
